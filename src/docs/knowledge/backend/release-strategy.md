# 灰度发布与 A/B 测试

> 发版不是"全量推"，而是"先放一小撮、验证没问题再全量"。本文讲清蓝绿/金丝雀/灰度/A-B 的区别、特性开关、回滚，以及如何借 K8s（见 `kubernetes.md`）落地，补发布工程视角（配合 `api-gateway.md`）。

## 一、为什么要灰度

渐进式发布把初始影响面缩小，配合可观测性和自动门禁更早发现回归。能否快速回滚取决于镜像、数据库、缓存、消息与外部副作用是否兼容，不能只看流量切回速度。

## 二、四种发布策略

| 策略                   | 做法                            | 优点           | 缺点                 |
| ---------------------- | ------------------------------- | -------------- | -------------------- |
| **蓝绿（Blue-Green）** | 新旧两套环境，验证后切流量      | 应用层切回快   | 资源与数据兼容成本高 |
| **金丝雀（Canary）**   | 小流量分阶段放量                | 控制初始影响面 | 需要可靠路由和门禁   |
| **灰度（Gray）**       | 按用户属性（白名单/地区）放部分 | 精准目标用户   | 需路由支持           |
| **滚动（Rolling）**    | 逐台替换（K8s 默认）            | 资源省         | 新旧共存期长         |

## 三、金丝雀示例（K8s）

```bash
# 用副本比例做近似实验；不能当严格 10% 流量保证
kubectl scale deploy/vc-server-v2 --replicas=1
kubectl scale deploy/vc-server-v1 --replicas=9
# 观察监控/错误率，OK 再逐步升 v2、降 v1
```

副本比例会受连接复用、请求耗时、session affinity 和负载均衡算法影响。需要严格权重、按 header/用户粘性和自动指标分析时，使用 Gateway/服务网格或渐进发布 controller，并验证实际流量分布。

## 四、A/B 测试

A/B 是对"产品策略"做对比实验：同一功能两个版本（A 旧 / B 新），按用户随机分流，用指标（转化率/留存）判断哪个更好。

- 与灰度区别：灰度验证"新版本没坏"，A/B 验证"新版本更好"。
- 分流要随机且稳定（同一用户始终同一组），靠用户 ID hash 路由。
- 统计设计：实验前定义主指标、护栏、最小可检测效应和停止规则；不能看到曲线领先就提前结束。

## 五、特性开关（Feature Flag）

```ts
if (flags.isEnabled('new-checkout', user.id)) {
  return <NewCheckout />
}
return <OldCheckout />
```

- 代码先合入但默认关，开关控制暴露；出问题关开关即回滚，不必发版。
- 工具：LaunchDarkly、Unleash、自研配置中心。
- 注意：开关堆积成"技术债"，下线后要清理分支代码。

Feature flag 分为 release、experiment、ops、permission 等类型。权限不能只靠前端 flag；服务端仍需授权。分组计算要稳定、可审计，并处理未登录到登录后的身份合并，避免同一用户在 A/B 间跳组污染实验。

## 六、回滚与观测

- **回滚**：应用镜像可用 `rollout undo`/蓝绿切回，功能可关开关；数据库和消息格式往往更适合向前修复，必须预先设计兼容窗口。
- **观测**：发布同时盯错误率/延迟/核心指标（见 `frontend-monitoring.md`），设告警阈值自动拦截放量。
- **预案**：放量前备好回滚命令与 on-call 通知。

## 七、与 VueChest 的衔接

- 前端静态资源带 hash（见 `vite.md`），新旧可共存；灰度靠网关/CDN 按用户返回不同资源版本。
- 后端多副本 Deployment 支持金丝雀；API 网关（见 `api-gateway.md`）按 header/用户做灰度路由。
- 新功能用特性开关包裹，先内部白名单验证再全量。

## 八、常见坑

- **灰度没监控**：放了不知道坏没坏 → 必须配套指标告警。
- **开关忘清理**：长期堆积难以维护 → 设下线计划。
- **A/B 样本不足就下结论**：伪显著 → 等统计显著。
- **回滚慢**：预案没演练，出事手忙脚乱 → 定期演练回滚。

## 九、数据库与契约兼容

滚动/金丝雀期间新旧版本同时运行，schema 变更遵循 expand-contract：

1. Expand：先增加可选字段、表或兼容 API，旧代码不受影响。
2. Migrate：双读/双写或后台回填，监控一致性与进度。
3. Switch：新代码切到新结构，保留旧读路径一段时间。
4. Contract：确认无旧实例/消费者后再删除旧字段与兼容逻辑。

重命名字段应拆成“新增 → 回填 → 切读写 → 删除”，不要在一次发布里直接 rename。消息消费者要容忍新旧 schema，缓存 key 加版本，前端旧 chunk 与后端新 API 也要有兼容周期。

不可逆数据迁移上线前做备份恢复演练、耗时估算和停止条件。应用回滚后若已经写入新格式，旧版本是否还能读取是必须回答的问题。

## 十、渐进发布门禁

典型阶段可以是内部员工 → 1% → 5% → 25% → 50% → 100%，但百分比和观察窗口由流量与风险决定。每阶段自动比较新旧 cohort：

- 技术 SLI：错误率、P95/P99、饱和度、崩溃、队列积压。
- 业务 SLI：支付/发布/登录等任务成功率，不能只看 HTTP 200。
- 数据质量：重复写、schema 错误、对账差异和权限拒绝。
- 成本护栏：外部 API、LLM token、数据库与网络成本。

低流量服务不能仅等待固定 5 分钟；需要足够请求量或合成探测。自动回滚阈值要防瞬时噪声，同时严重安全/数据破坏事件应立即停止，不等待统计显著。

## 十一、前端、缓存与异步任务

前端灰度必须让同一用户稳定拿到相容的 HTML/JS/API 组合。内容哈希资源保留旧版本，HTML/CDN 缓存键纳入经过验证的 cohort，Service Worker 更新也要避免混合版本。

队列中可能仍有旧版本生产的消息，worker 滚动后必须能处理；长任务开始于 v1、结束于 v2 时需要任务 schema/version 和幂等。定时任务/数据库 migration 通常只能有一个 leader，不能随副本数量重复执行。

## 十二、常见坑补充

- **用副本比例等同流量比例**：长连接和负载均衡让实际比例偏差很大。
- **只盯全局平均**：特定浏览器、地区、租户或高价值路径已严重回归。
- **应用回滚但数据库不兼容**：旧版本读取新 schema 失败，回滚反而扩大事故。
- **实验组不稳定**：用户跨设备/登录状态切组，指标互相污染。
- **Flag 默认值不安全**：配置中心超时时全量打开高风险功能。
- **没有 owner/expiry**：永久开关与死分支持续增加组合爆炸。

## 十三、发布决策清单

- [ ] 此次发布适合 rolling、canary、blue-green、flag 还是组合？
- [ ] 新旧应用、API、数据库、缓存和消息 schema 能否同时运行？
- [ ] cohort 是否稳定，实际流量比例和关键用户切片是否可见？
- [ ] 每阶段的请求量、观察时间、SLI、阈值和停止规则是否预先定义？
- [ ] 回滚、roll-forward、关 flag、停止消费者和恢复数据是否演练？
- [ ] migration/cron 是否单实例，副作用是否幂等且可审计？
- [ ] A/B 是否区分产品指标与可靠性护栏，统计方案是否预注册？
- [ ] 发布完成后是否清理旧资源、兼容逻辑和到期开关？

## 十四、小结

- 蓝绿（快回滚）/金丝雀（小步放量）/灰度（按属性）/滚动（省资源）按需选。
- A/B 验证"更好"、灰度验证"没坏"，目标不同。
- 特性开关让回滚变"关开关"；发布必配监控与回滚预案。
