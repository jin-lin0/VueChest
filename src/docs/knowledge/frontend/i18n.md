# 前端国际化（i18n）

> 产品要出海/服务多语言用户，i18n 是必过的坎。本文讲清多语言方案、文案抽离与占位符、复数与懒加载，以及和暗色模式/RTL 的协作，让"加一门语言"成为低成本动作（配合 `design-token.md` 的主题体系）。

## 一、i18n 三件事

1. **文案抽离**：所有用户可见文本不放硬编码，进语言包（key → 翻译）。
2. **运行时切换**：根据用户偏好/浏览器/`navigator.language` 选语言包并响应式切换。
3. **格式化**：数字/日期/货币/复数按区域规则（Intl API）。

## 二、Vue：vue-i18n

```ts
// i18n.ts
import { createI18n } from 'vue-i18n'
export const i18n = createI18n({
  legacy: false,
  locale: 'zh-CN',
  fallbackLocale: 'en',
  messages: {
    'zh-CN': { welcome: '欢迎，{name}' },
    en: { welcome: 'Welcome, {name}' },
  },
})
```

```vue
<template>
  <p>{{ t('welcome', { name: user.name }) }}</p>
</template>
<script setup>
import { useI18n } from 'vue-i18n'
const { t } = useI18n()
</script>
```

## 三、React：react-i18next

```ts
import { useTranslation } from 'react-i18next'
const { t } = useTranslation()
return <p>{t('welcome', { name: user.name })}</p>
```

## 四、关键实践

- **占位符**：`欢迎，{name}` 避免拼接字符串，保语序（不同语言词序不同）。
- **复数**：英文 `1 item` / `2 items`；用 i18n plural 规则（CLDR），别自己 if-else。
- **数字/日期/货币**：用 `Intl.NumberFormat` / `Intl.DateTimeFormat` 而非手动格式化。
- **懒加载语言包**：按 locale 动态 `import()` 语言包，首屏只载当前语言（见 `vite.md` 分包）。
- **key 管理**：用 `i18next-scanner` 自动提取模板中的 key，减少漏翻。

### 使用 `Intl`，不要手写区域规则

locale 不只是翻译语言。日期顺序、小数点、货币符号、单位和列表连接词都随区域变化；`zh-CN` 与 `zh-TW` 也不能只按 `zh` 处理。后端传输 ISO 时间、货币代码和原始数字，展示层再按用户 locale 格式化。

```ts
const locale = 'de-DE'
const price = new Intl.NumberFormat(locale, {
  style: 'currency',
  currency: 'EUR',
}).format(1234.5)

const date = new Intl.DateTimeFormat(locale, {
  dateStyle: 'medium',
  timeZone: 'Europe/Berlin',
}).format(new Date('2026-08-23T08:00:00Z'))

const files = new Intl.PluralRules(locale).select(2)
```

时区是独立于 locale 的业务选择：用户语言是中文，不代表时区一定是上海。涉及预约、账单和日志时同时保存 UTC 时间、业务时区和展示 locale，避免只保存格式化字符串。

## 五、与主题/RTL 协作

- **RTL（阿拉伯语等）**：`<html dir="rtl">` 翻转布局；CSS 用逻辑属性（`margin-inline-start` 而非 `margin-left`）天然适配（见 `layout.md`）。
- **暗色 + 语言**：语言和主题是独立维度，都用各自的状态/Tokens 管理（`tokens.css` 管主题，`i18n` 管语言）。

## 六、常见坑

- **文案硬编码**：开发时图快直接写中文，出海时全量返工 → 一开始就抽离。
- **拼接字符串**："{count} 条评论"在不同语言顺序不同 → 用占位符。
- **漏翻/默认回退**：缺 key 时显示 key 本身很难看 → 配 `fallbackLocale` 且监控缺失。
- **长度膨胀**：德语文案常比英长 30%，UI 留白与溢出处理要预留。
- **翻译 HTML**：允许语言包注入任意 HTML 会扩大 XSS 风险。优先组件插值，确需富文本时限制标签并清洗。
- **只截语言前两位**：`pt-BR`、`pt-PT`、简繁中文可能差异明显。按完整 locale → 语言 → 默认语言建立回退链。
- **把 key 当原文**：原文变化会导致 key 失效或翻译复用混乱。使用稳定的语义 key，并保留上下文说明。

## 七、语言包加载与切换

首屏语言可由已登录偏好、显式 Cookie、URL 前缀和 `Accept-Language` 依次决策；一旦用户手动选择，就应覆盖浏览器默认。SSR 时服务端和客户端必须使用同一 locale，否则会 hydration mismatch。

```ts
const loaders = {
  'zh-CN': () => import('./locales/zh-CN.json'),
  en: () => import('./locales/en.json'),
} as const

type SupportedLocale = keyof typeof loaders

async function setLocale(locale: SupportedLocale) {
  const messages = (await loaders[locale]).default
  i18n.global.setLocaleMessage(locale, messages)
  i18n.global.locale.value = locale
  document.documentElement.lang = locale
  document.documentElement.dir = locale === 'ar' ? 'rtl' : 'ltr'
}
```

动态导入要有加载态、失败回退和并发保护，避免用户快速切换时旧语言包最后返回并覆盖新选择。缓存 key 应包含语言包版本，部署删除旧 chunk 时还要处理打开很久的旧页面加载失败。

## 八、翻译协作与测试

- 给译者提供截图、字符限制、变量含义和复数上下文，不能只交一列 key。
- CI 检查各 locale 缺失 key、无效占位符和多余 key；占位符集合必须与源语言一致。
- 伪本地化把文案拉长并加入特殊字符，提前发现截断、编码和硬编码。
- 视觉回归至少覆盖最长文案、RTL、窄屏、日期/货币和复数边界。
- 日志记录缺失 key，但要聚合去重，不能在生产控制台无限刷屏。

## 九、方案决策清单

1. 明确支持的 locale、时区、货币和回退链，不把它们混成一个字段。
2. 选择带 ICU/CLDR 复数与插值能力的库，禁止业务手写语言规则。
3. 决定 URL 是否包含 locale；需要 SEO 时通常使用独立可索引路径和 hreflang。
4. 首屏语言包内联或预加载，低频语言动态加载并做好失败恢复。
5. 切换时同步 `lang/dir`、持久化偏好，并确保 SSR 与 hydration 一致。
6. 上线前执行 key/占位符检查、伪本地化、RTL 与辅助技术测试。

## 十、小结

- i18n = 文案抽离 + 运行时切换 + Intl 格式化。
- 占位符保语序、CLDR 管复数、懒加载降首屏。
- RTL 用 `dir` + CSS 逻辑属性；与暗色主题正交管理。
