# 牛客全量标准答案 · 六、AI / Agent（前端 Agent / AI 研发）

## Agent 基础

### 介绍一下 Agent 的核心组成模块（规划 / 记忆 / 工具 / 行动）？给新同事解释 Agent 四大核心模块你会怎么讲？Agent 与传统 Workflow 的核心区别？

> “我把 Agent解释成一个围绕目标持续做‘观察—决策—行动—再观察’的系统。规划把目标拆成步骤；工作记忆保存当前状态，长期记忆提供跨会话知识；工具把模型连接到检索、代码或业务系统；行动执行工具并读取结果。外层还必须有状态机、权限、预算、评测和人工确认。传统 Workflow的路径和分支大多由开发者预先定义，Agent允许模型根据中间结果动态选择下一步；生产系统常是确定性 Workflow包住局部 Agent，而不是二选一。”

### Agent 和普通 Chatbot 的区别？已有成熟大模型，为什么还需要智能体？Agent 能帮大模型解决哪些原生处理不了的问题？

> “普通 Chatbot主要根据当前上下文生成文本，Agent还拥有目标、状态、工具和迭代控制，能够查实时数据、执行操作并根据结果修正。成熟大模型的参数知识仍可能过时，不能直接访问企业私有系统，也不能可靠地产生外部副作用；Agent用 RAG补知识、工具连接系统、记忆保持任务状态、编排完成多步工作。但如果只是稳定问答或单一 API调用，我不会为了‘智能’引入 Agent的成本和不确定性。”

### ReAct 的执行流程是什么？ReAct / Plan-and-Execute / Reflection 的区别？ReAct 比单纯 LLM 强在哪？实际开发中如何避免"思考与行动脱节"？Planning 是由框架还是大模型做的、有哪些方法？

> “ReAct让模型在每轮基于当前观察选择行动，工具执行后把结果作为新观察继续循环；工程上不需要暴露私有思维链，只保存简洁决策摘要和结构化动作。Plan-and-Execute先生成较高层计划，再逐步执行和必要时重规划，适合长任务；Reflection是在结果或失败后由模型/规则评审并修正。ReAct比一次生成强在能接触外部事实和闭环纠错。Planning通常由模型提出、框架用状态机和 schema约束，关键步骤由规则或人审批，避免计划写了一套、执行器却不验证前置条件。”

### Function Calling / Tool Calling 的完整流程？Agent 的自主决策、工具调用链路怎么设计？什么场景下建议用多 Agent 而不是一个全能 Agent？

> “Tool Calling链路是：应用向模型提供工具名、用途和 JSON Schema；模型返回一个或多个带 callId的结构化调用；宿主校验参数、鉴权和策略，执行工具并记录审计；结果按 callId回填；模型再决定继续调用还是生成答案。自主性来自模型选择，但执行权始终在宿主。多 Agent只在角色需要不同权限/上下文、任务可并行、独立评测或故障隔离时采用，例如研究与合规审核；否则一个 Agent加明确工具更简单，避免通信损耗和错误放大。”

### 如何设计一个 Agent（要考虑哪些模块）？Agent 的循环执行逻辑、依靠什么条件判断循环结束 / 输出结果？success / failure 状态由什么机制判定？Agent 循环是否以本轮是否调用工具作为结束判断？

> “设计时我先定义目标和成功标准，再设计状态、模型、提示、工具契约、记忆、权限、预算、观测和评测。循环状态至少包含 ready、running、waiting_approval、succeeded、failed、cancelled；每步验证工具结果是否满足子目标，并更新可持久化状态。结束条件包括验收器通过、模型提交 final且规则允许、用户取消、不可恢复错误、超时/步数/Token/成本上限。‘这一轮没调用工具’不能作为唯一成功判断，它也可能是模型漏调；success应由确定性断言、结构化 evaluator或人工确认判定，failure要有分类与可重试性。”

### 多 Agent 系统怎么协作？常见架构（中心化 / 去中心化 / 分层）？主子 Agent 架构、子 Agent 之间上下文怎么传递？子 Agent 失败如何重试 / 降级？

> “中心化架构由 supervisor拆任务、分发和汇总，治理简单但有单点；去中心化让 Agent点对点协商，灵活却难追踪；分层架构让总控管理领域 supervisor，再管理专业 Agent，适合规模化。主 Agent只给子 Agent最小任务包：目标、输入引用、约束、权限、截止时间、输出 schema和 traceId，不直接复制全部对话。子 Agent返回结构化结果、证据和状态。失败按错误类型有限重试，换模型/工具或降级为单 Agent，关键任务转人工；重试必须幂等并有总预算。”

### 多个 Agent 同时跑时 State 管理与 Checkpoint 机制、状态竞争怎么避免？两个 Agent 协作（如生成文案 + 审核合规）之间怎么通信（结构化消息 vs 自然语言）？如果一个 Agent 宕机或超时另一个怎么处理？

> “共享状态要有单一权威存储、任务版本和原子条件更新；每个 Agent只写自己拥有的字段，checkpoint记录 state版本、输入引用、工具调用和可恢复游标。竞争用乐观锁、幂等键或队列串行化，不能靠最后写入覆盖。文案 Agent给审核 Agent发送 `{content, policyVersion, evidence}` 等 schema，解释可以是自然语言字段，但状态和决策必须结构化。每个任务有租约、heartbeat和 deadline；宕机后由调度器回收并从 checkpoint恢复，超时则取消下游、降级或转人工。”

### 多模型如何动态路由（按任务 / 成本 / 延迟 / 效果选模型）？所有模型超时或故障怎么兜底、何时规则引擎、何时人工、恢复后怎么回切？能否让系统自动发现问题、尝试策略、验证效果并自动生效和回滚？

> “路由先按任务能力和合规过滤候选，再用离线质量、实时成功率、P95延迟、上下文长度与单位成本打分；高风险任务可先小模型分类，再交高能力模型。路由和 fallback都要灰度，熔断单模型/区域，所有模型故障时回规则引擎、缓存结果、排队或人工，不能无限级联重试。恢复后先小流量半开探测再渐进回切。系统可自动发现指标异常、在沙箱尝试提示/路由策略并跑回归评测，但自动生效只限低风险且有门禁、变更记录、canary和自动回滚，高风险仍需审批。”

### Agent 死循环、工具循环调用如何处理？执行太长或死循环怎么解决？Agent 模式怎么实现"图片定位代码"？Agent 模式的底层实现逻辑？

> “防死循环我会同时设置最大步数、墙钟时间、Token和成本预算，记录最近工具名+规范化参数+结果摘要，检测重复无进展、状态不变和往返振荡；命中后要求重规划一次，再失败则停止或人工。工具按幂等键执行并有超时/熔断。‘图片定位代码’可由视觉模型提取界面元素与坐标/文本，再通过源码索引、组件树、sourcemap和截图差异把视觉区域映射到候选文件，最后由工具读代码和验证修改。底层仍是模型决策、受控工具执行、观察回填和状态机循环。”

### 如何控制 Agent 的「自主性」边界（严格规则引擎 vs 允许自主推理）？如何设计安全护栏（Safety Guardrail）？

> “自主性按风险分级：只读检索可自动；可逆的本地修改可在沙箱自动并要求测试；外部写入、付费、发布、删除和涉及个人数据的动作必须最小权限并在提交前人工确认。护栏不是一条提示词，而是输入检测、工具白名单与严格 schema、服务端鉴权、数据隔离、出网控制、速率/预算、输出校验、审计和事故回滚。模型负责在允许空间里推理，规则引擎负责不可违反的硬约束；不让模型自己判断是否可以绕过护栏。”

### 接到一个新需求时，应该用一个普通 API / 函数调用解决，还是用 Agent（自主规划 + 工具调用）来解决？各自的适用边界与判断标准是什么（如何判断一个需求该用确定性代码 / API 还是自主 Agent）？

> “我用不确定性和闭环次数判断。输入输出固定、规则明确、一次调用可完成、错误代价高的需求优先普通函数/API或 Workflow；需求开放、步骤取决于中间观察、需要跨工具搜索与修正时才考虑 Agent。还要看是否有可验证成功标准、工具是否安全幂等、延迟成本是否可接受。通常先实现最小确定性流程，把真正无法预枚举的决策点交给模型；如果 Agent上线后大多数轨迹固定，再反向固化成 Workflow以降低成本和波动。”

## 记忆与上下文

### Agent 的记忆机制有哪些（短期 / 工作 / 长期）？短期记忆具体实现方式（窗口上限、达到上限让 Agent 总结、保留最近几轮）？长期记忆怎么设计（静态 / 动态）？什么时候触发存储？如何防止记忆膨胀（去重 / 淘汰）？

> “短期/工作记忆保存当前任务目标、最近对话、计划、工具结果和未完成状态，放在上下文或外部 checkpoint；接近预算时保留系统约束、当前目标和最近原文，把较早内容滚动总结。长期记忆分静态知识与动态用户/任务记忆，存外部数据库并带来源、时间、置信度、权限和版本。只有明确偏好、反复有用事实或用户主动要求才写入，敏感信息需同意和保留策略。用指纹/embedding去重、衰减、TTL、容量上限和周期合并防膨胀，写入与召回都要评测。”

### 每一轮对话如何逐步叠加到上下文？如何判断"快到上限了"、什么时候触发总结？长短期记忆的区别、短期记忆里会存储 function call 内容吗？

> “每轮不是简单把所有消息无限拼接，而是维护消息日志和一个可组装上下文：固定指令、任务状态、相关长期记忆、摘要、最近若干轮和必要工具证据。用目标模型 tokenizer预估输入+预留输出+工具 schema的总预算，在到达例如安全阈值前触发摘要，并验证摘要保留目标、决策、约束、实体和未完成项。短期记忆会保存 function call的工具名、参数、callId、状态和结果，但大结果只保留摘要与可检索引用，敏感字段脱敏。”

### 大模型怎么决定长期记忆是否需要召回？更新策略、是否遇到过记忆污染？企业级记忆中用户纠错（不一定对）怎么处理？多个窗口对话记忆性、所有对话用户画像怎么做？

> “模型不应独自决定长期记忆召回。系统先按用户/租户/权限过滤，再用查询改写、时间、语义、关键词和重要度取候选，rerank后把少量证据注入，并标记来源。更新采用 append+版本或字段级合并，冲突不静默覆盖。用户纠错也只是带来源的声明，涉及企业事实要与权威系统核对；被检索内容永远当数据而非指令，防记忆污染。跨窗口用户画像按明确 schema保存稳定偏好和授权事实，允许用户查看、纠正和删除，不把模型推断偷偷固化为事实。”

### 上下文窗口 / Token 超限怎么办？上下文压缩机制怎么做（滚动摘要 / 截断阈值 / LLMLingua / Rerank / Map-Reduce）？对上下文渐进式披露的理解（Claude Code 的渐进式披露机制）？

> “Token超限时先删无关工具定义和重复内容，再检索只取相关片段；早期对话滚动成结构化摘要，大文档做分层 Map-Reduce或父子块检索，关键原文通过引用按需展开。LLMLingua类压缩可缩短提示，但必须验证事实和指令不丢；rerank用于选择，不等于摘要。渐进式披露是先只给目录、元数据或技能摘要，模型选中后再加载正文、文件片段和工具结果，使上下文随任务需要展开。任何压缩都要保留不可丢的权限、验收标准和当前状态。”

### 上下文里筛选哪些内容、从哪获取、什么时机注入、如何保证需要的内容成功注入？除会话窗口长度、上下文压缩外，上下文还有哪些技术点？

> “上下文工程要回答四问：需要什么、从哪里取、何时注入、如何验证。来源包括系统规则、用户消息、任务状态、代码/文档检索、工具结果和授权记忆；先做权限过滤与相关性排序，在规划前注入目标与能力，在具体步骤前按需取证，在最终回答前补引用。保证注入靠必需字段断言、coverage/eval和缺失时主动检索，不靠提示词祈祷。其他关键点还有位置与顺序、来源可信度、缓存、去重、陈旧检测、跨模态表示、敏感信息最小化和 prompt injection隔离。”

### 多 Agent / 多异步任务场景下怎么防止上下文污染？多轮对话 / 长文本怎么处理？

> “每个 Agent/异步任务使用独立 contextId、消息命名空间和只读输入快照，只通过结构化结果合并；工具响应用 callId匹配，晚到结果若版本不符就丢弃。共享事实写入版本化状态库，合并由 supervisor或 reducer按规则完成，不能让多个 Agent直接改同一段 prompt。长对话维护事件日志、摘要和检索索引；长文档先解析结构、分块、检索与父块补全。最终上下文还要做来源标记和注入扫描，防止一个子任务的不可信内容升级成全局指令。”

## Skill 与工具调用（MCP / Skill / Function Calling）

### 你对 Skill 的理解是什么？Skill 与传统提示词工程、MCP 三者之间差异？Skill 分层体系（内置 / 用户 / 项目）？用户输入怎么和 Skill 匹配 / 路由？有没有 Skill 沉淀机制？Rules 和 Skills 的区别、为什么不把 Skills 指导写进 Rules？

> “我把 Skill理解为可复用的任务方法包：说明何时使用、工作流程、约束、模板，并可附脚本和资料；提示词通常只是一次或一段指令，MCP则是 Agent发现并调用外部工具/资源的协议。Skill可按内置、用户和项目覆盖层组织，路由先看名称/描述和显式触发，选中后渐进加载完整内容。成熟做法会把复盘中的通用流程沉淀为版本化 Skill并评测。Rules是始终生效的全局硬约束，Skills只在相关任务加载；把所有 Skill写进 Rules会占上下文、互相冲突且让模型难以选择。”

### Function Calling / Tool Calling 完整流程？MCP 与 Function Calling 的区别、两者关系？MCP 与本地 tool 有什么不同？MCP 的核心工作流程？MCP 最新技术（SSE 与 HTTP streamable 区别）？MCP Server 怎么知道哪个用户调用了哪个工具？MCP 与 Skills 的区别、能否只用 skill + 脚本替代 MCP？CLI 与 MCP 区别？A2A 协议、SubAgent 是什么（MCP 是 AI 与工具连接标准，A2A 是 AI 与 AI 连接标准）？

> “Function Calling是模型输出结构化工具请求的能力；MCP把工具、资源等能力的发现和调用标准化，让不同客户端连接不同服务器，模型仍可通过自身 Tool Calling决定使用其中哪个能力。本地 tool与远程 MCP的执行位置不同，但都必须由宿主鉴权。当前 Streamable HTTP可用普通 HTTP响应并按需流式，早期独立 HTTP+SSE传输已是旧模式；stdio适合本地进程。用户身份由客户端到服务器的认证上下文、token/会话和审计字段传递，不由模型口述。Skill是操作方法，CLI是命令界面，MCP是连接协议；Skill+脚本能替代简单本地任务，但难替代跨客户端发现、授权和远程治理。A2A面向 Agent间任务协作，SubAgent是主任务下受控的子执行者，两者也不是 MCP的同义词。”

### MCP 的传输方式（SSE / 流式）？开发一个 MCP 服务器的大概思路？MCP 返回结果支不支持流式？MCP 负载很高不堪重负怎么解决？MCP 有什么安全问题、如何解决？把某个接口封装成 MCP 工具时标准化接口怎么设计、兼容性问题？

> “开发 MCP Server时先定义最小能力和权限，为每个工具写精确名称、描述、输入/输出 schema和错误模型，再实现发现、调用、认证、超时、限流、日志与版本兼容；本地可走 stdio，远程用 Streamable HTTP。工具结果本身可以返回内容或资源引用，长任务更适合返回 taskId并通过协议支持的进度/轮询或流式通道更新，不能假设任意业务函数都天然 token流式。高负载用无状态扩容、队列、缓存、并发配额和熔断。安全上防过宽权限、参数注入、SSRF、数据泄漏和 confused deputy，高风险调用需用户确认与审计。演进只加可选字段或发布新工具版本，避免悄悄改变语义。”

### Skills 与大模型交互的流程？大模型怎么调用 Skills（仓库有 100 个 Skills 时上下文怎么办、意图识别 / 渐进式披露）？skills 输出结构化数据如何保障大模型输出 JSON 格式？怎么写一个 skill？

> “系统先用 Skill元数据匹配意图，只把少量候选名称和摘要放上下文；模型选中后再加载完整 SKILL、所需参考和脚本，这就是仓库有上百 Skill时的渐进披露。执行过程仍由宿主提供文件/工具能力，Skill本身不是魔法 API。结构化输出要定义 JSON Schema，使用模型的结构化输出/工具调用，并在宿主做 parse、schema校验、有限修复和失败重试，不能只写‘请返回 JSON’。编写 Skill要包含触发边界、输入、步骤、验证、失败处理和最小必要资源，并用正反例评测是否误触发或漏触发。”

### Agent 怎么决定调哪个工具？配置了十多个工具怎么避免模型选错（工具描述模板化、每步只推荐一个工具）？工具调用的 Schema 设计核心（名字精准 / 描述说清何时调 / 参数 schema 严格）？如何减少工具过多带来的 Token 消耗？

> “工具选择质量首先由工具设计决定：名称具体、描述写清何时用/何时不用、参数严格且枚举和必填明确，避免多个工具语义重叠。十多个工具时先由确定性权限和任务阶段过滤，再用轻量路由召回2～5个候选；关键步骤甚至只暴露允许的一个工具。大工具集通过命名空间、服务器发现和按需加载降低 token。执行前宿主校验 schema、业务前置条件和权限，低置信或高风险时确认。工具描述需要版本化 eval，统计误选、漏选和参数错误，而不是不断往系统提示里堆例子。”

### 大模型经常捏造工具调用参数、返回 JSON 不标准怎么解决？工具调用失败 / 超时 / 结果冲突怎么处理？模型回答不稳定怎么评估和兜底？

> “参数捏造用严格 schema、enum/format、`additionalProperties:false`、结构化输出和服务端校验解决；缺失事实就让模型先查工具，不能猜 ID。工具失败按超时、限流、鉴权、业务冲突和不可恢复错误分类，幂等请求有限退避重试，冲突用权威版本重读，高风险不自动重放。并行结果冲突保留来源、时间和置信度，由规则或验证工具裁决。稳定性用固定数据集多次运行，评估任务成功、工具选择、参数准确、轨迹长度、延迟和成本；线上再加规则 fallback、缓存、人工和可回滚版本。”

### 动态加载 Tool 与 Tool 注册怎么做的？未来 Tool 变多怎么优化？工具的统一调度和审计？大模型产生流式结果、结果只拿到一半怎么办（前端侧）？能否让大模型自己排除 api 超时和报错（SKILL）？

> “Tool注册表保存名称、版本、schema、权限、租户、健康度和执行端；会话开始只发现相关命名空间，真正调用前再加载完整定义。数量增长后做语义/规则路由、去重、弃用策略和能力契约测试。统一调度器负责 callId、鉴权、限流、超时、幂等、重试、熔断和审计。流式只到一半时前端把消息标记 interrupted，保留 eventId和已确认内容，可续传则带游标，否则让用户重试，不伪装完成。Skill可以教模型在 API超时后查健康、换只读源或降级，但错误分类、最大次数和禁止动作必须由调度器硬编码。”

### Skill 和 Tool 有什么区别？你的 Agent 里用了 Skill 还是 Tool、分别在什么场景下用？

> “Tool是可执行能力，例如查订单、搜索代码、写文件，有明确参数和结果；Skill是完成一类任务的方法，可能编排多个工具、模板和检查步骤。我的 Agent里会用 Tool连接外部事实和副作用，用 Skill沉淀‘如何做代码审查/RAG评测/发布检查’这类可复用流程。一个 Skill可以调用多个 Tool，也可以只提供知识；一个 Tool不应隐含长篇业务策略。回答项目时我会给真实实例和触发方式，若实际只用了工具就不会为了术语说成有 Skill系统。”

## RAG

### 介绍一下 RAG 的整体流程？RAG 解决了大模型的什么核心问题（幻觉 / 知识过时 / 私有数据）？为什么不能只做一次向量检索、线上系统怎么做？早期用 RAG 后来又不用了的原因？

> “RAG链路是采集与权限校验、解析清洗、结构化分块、embedding与索引；查询时做意图识别/改写、元数据过滤、关键词+向量召回、融合与 rerank，再把带来源证据交给模型生成并引用。它补充私有和新知识、降低无依据回答，但不能保证零幻觉。线上不能只做一次向量 top-k，因为关键词、时间、权限、对话指代和精排都会影响结果。若知识很小且稳定、可直接结构化查询，或检索延迟/维护成本高于收益，我会移除 RAG，改规则、工具或直接上下文，并用评测证明。”

### RAG 中如何选择 Chunk Size / Chunk Overlap？chunk 怎么切（语义段落、带多级标题索引）、大小一般多少、决定依据？PDF 中文分块如何实现？

> “Chunk没有通用最佳大小。我按模型 tokenizer、文档结构、问题粒度和召回/生成预算调参：子块要能独立表达一个主题，常从几百 token起做网格实验，overlap只用于跨边界语义且避免重复召回。优先按标题、段落、列表、代码和表格切，保存多级标题、页码、父块和权限元数据，超长段再递归切。中文 PDF先区分文本层和扫描页，做版面分析、阅读顺序、OCR、页眉页脚去除与表格单独抽取；不能按固定字符数把标题和正文切散。”

### embedding 模型选型？如何判断向量相似度（余弦相似度 / 欧几里得距离，工程应用区别）？除了余弦还了解哪些相似度算法？

> “embedding选型看领域/语言、多语、输入长度、维度、吞吐、许可证、部署和在自有检索集上的 Recall@n/NDCG，而不是只看榜单。余弦比较方向，常用于归一化语义向量；点积同时受模长影响，归一化后与余弦排序等价；欧氏距离关注几何距离，单位归一化向量下也有对应关系。还可用曼哈顿、Jaccard、BM25和学习式 cross-encoder相似度。换模型必须重建向量或使用兼容迁移，线上索引、查询向量和距离度量必须匹配。”

### 向量召回和 BM25 关键词召回各自适合什么场景？为什么做混合检索（全文索引 + 向量索引）？多阶段 RAG（BM25 + 向量混合）融合逻辑怎么设计？在什么环节提升效果？

> “向量召回擅长同义改写和语义相关，BM25擅长精确词、编号、错误码、人名和稀有术语；混合检索能互补。流程上分别取较大的候选集，先做权限/时间过滤，再用 RRF等对排名归一融合，避免直接相加不可比分数，最后用 cross-encoder或 LLM rerank到较小 top-k。效果可在查询改写、chunk、元数据过滤、召回参数、融合权重、rerank和上下文组装各环节提升。权重按查询类型或离线数据学习，不能用一组拍脑袋参数覆盖所有领域。”

### Rerank 在 RAG 链路里起什么作用、什么时候必须加？重排序怎么做？

> “Rerank用更强的 query-document联合模型重新判断候选相关性，修正 embedding只做独立编码造成的细粒度排序误差。它在候选多、问题复杂、相邻文档很像或 top-k质量直接影响高风险回答时价值大；小知识库、关键词精确命中或严格低延迟场景可不加。常见做法是 BM25+向量召回50～200条，去重后 cross-encoder打分，再选5～15条并做多样性/父块补全。是否‘必须’由 Recall@n、NDCG、最终答案和新增延迟/成本的 A/B评测决定。”

### RAG 召回率低 / 幻觉怎么排查与治理？召回率怎么提高？为什么向量检索分数高不一定好？为什么对话直接拿用户原话去检索效果不好？RAG 与微调怎么选？

> “我先拆成解析、索引、召回、排序、上下文和生成六段，用有标注 query逐段看：正确文档是否入库、权限是否过滤错、Recall@k是否命中、rerank是否把它压下、模型是否引用证据。提高召回可做独立问题改写、多查询、混合检索、父子块、metadata和领域 embedding。相似度高只表示向量近，不代表事实能回答，重复模板甚至会虚高。多轮用户原话含代词和省略，应压成独立查询。知识更新/私有事实选 RAG；需要稳定改变风格、格式或行为且有高质量训练数据才考虑微调，两者可组合。”

### RAG 系统如何评估、为什么不能只看最终答案？准确率多少？向量用的什么索引、数据量多大、查询延迟多少？向量检索准确性怎么评估校验？

> “RAG评估分层：摄取看解析完整率与元数据；检索看 Recall@k、MRR、NDCG和权限正确率；上下文看精确率、重复率；生成看 faithfulness、答案正确、引用支持率和拒答；系统看延迟、成本和稳定性。只看最终答案会掩盖模型凭参数答对或检索正确却生成错。索引可用 HNSW、IVF等，但参数必须结合数据规模和延迟实测。准确率、文档量、P95都只能报项目真实数据；没有就说明如何构建标注集、比较 exact search与 ANN并做线上抽检，绝不编数字。”

### 知识库如何构建？一万个长文档怎么构建 RAG 知识库？知识检索如何提升回答正确率？如何解析知识库中的表格 / 图片文件？

> “一万篇长文档我会做增量 ETL：对象存储保存原件，解析服务提取正文、标题、表格/图片和权限，内容 hash去重，按结构生成父子块，批量 embedding后写全文与向量索引，版本表支持更新、删除和重建。检索用查询改写、权限过滤、混合召回、rerank和引用。表格要保留行列标题与单元格关系，可生成结构化 JSON和面向检索的行摘要；图片先保留页码/位置，按需做 OCR、caption或多模态 embedding。队列、checkpoint、失败重试和数据质量报表保证长任务可恢复。”

### PDF 扫描件 / OCR / 表格结构化处理过程中踩过什么坑？识别准确率能到多少？

> “扫描 PDF常见坑是倾斜、旋转、低分辨率、双栏阅读顺序、页眉页脚重复、中文标点、合并单元格和跨页表格。流程应先做页面分类和图像预处理，再做版面检测、OCR、表格结构识别，并把 bbox、页码和置信度保留下来；低置信字段进人工校验。‘准确率’必须定义字符、字段还是整表准确率，并按真实文档类型分层抽样；不能给一个脱离数据集的百分比。上线还要监控供应商/模型版本漂移和原件可追溯性。”

### RAG 引用标注和可解释性怎么实现（回答的某句话如何关联到对应文档）？前端处理 RAG 知识库引用失效与权限不足的交互降级？

> “摄取时给每个 chunk稳定 citationId，保存 documentId、版本、页码/段落、bbox、权限和原文 hash；生成时只允许模型引用候选 citationId，服务端校验引用存在且相关，前端把答案 span映射到可展开原文。更严格可让生成结果输出 claim-citation结构，再做 NLI/LLM支持性校验。文档删除、版本变更或权限不足时，前端不展示泄露的标题/片段，标注‘来源已不可用’，允许重新检索或请求权限；答案若失去关键证据则降低可信状态，而不是保留看似有效的死链接。”

### 项目中用了几个模型（embedding / 路由 / LLM / Rerank）？LLM Wiki 了解过吗？

> “一个 RAG系统常有 embedding、查询路由/改写、rerank和生成模型，也可让同一 LLM兼任多个角色；模型越多并不越先进，关键是质量、延迟、成本和运维边界。项目回答必须说真实用了几个、各自为什么选、版本和评测。LLM Wiki通常指利用 LLM从代码/文档生成结构化知识库或 Wiki的一类产品/方案，不是唯一标准技术；我会关注它的解析、引用、增量更新、权限和幻觉控制，而不是只说听过名字。”

### 为什么要先切分父子块、再做 embedding（父子分块 / small-to-big 检索带来的收益，子块召回、父块补全上下文）？

> “小块更容易与精确问题语义匹配，但直接交给生成模型可能缺少定义和上下文；大块上下文完整，却容易把 embedding语义平均稀释。父子分块同时保留二者：对子块做 embedding和召回，命中后按 parentId取父段或相邻块，再去重、rerank并受 token预算限制。这就是 small-to-big。父块不能无限扩展，否则会重新引入噪声；要在有标注检索集上比较 chunk命中率、答案支持率和上下文成本。”

## 框架与选型

### LangChain 和 LangGraph 的区别？为什么用 LangGraph 而不是简单 LangChain？为什么选 LangChain、不直接调 OpenAI 接口？不用现成框架而自研的利弊？

> “LangChain提供模型、工具、检索器和常见 Agent loop等高层抽象与集成；LangGraph更偏低层、显式状态图和持久化运行时，适合长任务、分支循环、checkpoint、streaming和 human-in-the-loop。简单问答或一次工具调用直接 SDK最透明；需要多供应商/组件集成可用 LangChain；复杂可恢复编排才用 LangGraph。自研能精确控制协议、依赖和性能，但要自己承担状态、重试、观测和升级。选型依据复杂度与退出成本，不因为框架热门。”

### Agent 框架你用过哪些（LangChain / LangGraph / CrewAI / Coze / Dify / LlamaIndex / Eino / Agentscope 等）？各自优缺点？Coze / 扣子是 Agent 平台还是工作流平台？

> “我不会假装所有框架都深度使用。LangChain集成广、上手快；LangGraph适合显式有状态编排；LlamaIndex强项是数据摄取、索引和 RAG；CrewAI/AgentScope偏多 Agent角色协作；Dify、Coze等平台同时提供 Agent与可视化 Workflow/应用发布能力，具体边界随产品版本变化；Eino面向 Go生态。面试时我会选自己真实做过 PoC的两三个，从状态持久化、工具协议、调试、评测、部署、锁定效应和团队语言比较，并说明为什么项目最终选或没选。”

### SpringAI 的核心作用和适用场景、怎么实现记忆管理、与直接用 AI SDK 的区别？AI 应用框架应该学哪一门（围绕模型、工具、记忆、编排、范式）？

> “Spring AI把 Java/Spring生态中的模型客户端、提示、工具调用、向量库、RAG、ChatMemory、MCP和可观测做统一抽象，适合已有 Spring服务和治理体系。记忆可用滑动消息窗口加 ChatMemoryRepository，完整历史应另存；工具调用中间消息是否持久化要核对具体实现。直接 SDK依赖少、能力最新且行为透明，Spring AI则减少供应商切换和基础设施集成成本。学习框架不应按名字堆栈，而要掌握模型、工具、记忆、检索、编排、评测和安全这些可迁移范式。”

### 前端 Agent 项目技术选型（为什么选 Go / TypeScript）？整个对话平台链路、Agent 分层架构（UI 层 / 模型层 / 中间层）？

> “前端/Node中间层选 TypeScript可共享消息 schema、工具类型和 UI生态，开发迭代快；Go适合高并发网关、流式代理、任务调度和资源可控的独立服务。最终按团队、部署和性能实测选择，不是 Go一定快或 TS不能做后端。链路通常是 UI管理会话与流式状态，BFF做鉴权、协议归一和 SSE/WebSocket，Agent层做编排/记忆/工具，模型网关做路由限流，工具服务访问业务系统，状态与 trace落库。每层都传播 conversationId、messageId、generationId和取消信号。”

## 大模型基础

### 什么是大语言模型，与传统 NLP 模型本质差异？Token 是什么？同一段文本在不同模型 Token 数可能不同、怎么计费？上下文窗口的本质、与会话记忆的关系？

> “大语言模型通过大规模自监督预训练学习下一个 token分布，再经对齐适配通用生成；传统 NLP常为单任务、较小模型和专门特征/头部，两者不是绝对分界。Token是 tokenizer把文本映射的子词/字节单元，不同模型词表和算法不同，所以同一文本 token数不同。计费通常按输入、缓存输入、输出等 token类别和模型单价，必须以供应商当前规则为准。上下文窗口是单次推理可见 token上限，不等于模型会永久记住会话；跨调用记忆由应用重新注入或外部存储实现。”

### Self-Attention 的本质、计算步骤？QKV 为什么要这么分？同一个 token 向量每次一样吗？Encoder 与 Decoder 各负责什么、为什么现在大模型大部分 Decoder-only？RoPE 是什么、相比绝对位置编码优势？GQA / MHA / MQA 区别？LayerNorm 与 RMSNorm 区别、为什么要 LN？

> “Self-Attention把输入分别线性映射为 Q、K、V，用 `softmax(QKᵀ/√d)`得到相关权重，再加权 V；多头在不同子空间建模。Q表示当前要找什么，K表示可匹配特征，V是被聚合内容。同一 token的初始词向量可相同，但加位置和上下文层后表示不同。Encoder双向编码输入，Decoder用因果 mask自回归生成；Decoder-only统一预训练与生成且扩展简单。RoPE通过旋转把相对位置信息融入 Q/K。MHA每头独立 K/V，MQA共享一组，GQA按组共享以折中质量和 KV缓存。LayerNorm中心化并缩放，RMSNorm只按均方根缩放更简洁；归一化稳定激活和梯度。”

### 采样参数 Temperature / Top-k / Top-p 怎么用？涌现能力是什么？弱 AI 与强 AI 区别？

> “Temperature缩放 logits，越低越确定；top-k只在最高 k个候选采样，top-p取累计概率达到 p的动态集合。事实抽取/工具参数用低随机性，创意任务适当提高，但不要同时极端调整多个参数；固定 seed也未必跨版本完全复现。涌现能力指规模增长时某些评测能力看似突然出现，但部分现象也受指标阈值影响。弱 AI指面向特定任务的系统，强 AI/AGI指接近通用人类智能的假设目标；当前产品工程应按可测能力设计，不用哲学标签替代评估。”

### 什么是大模型幻觉？如何缓解（提示词 - 工具 - RAG - 微调）？降低幻觉、提升 Agent 流程稳定性？Agent 产生幻觉 / 乱调工具怎么缓解？

> “幻觉是模型生成了流畅但无事实或工具依据的内容。治理按链路分层：提示明确证据边界和可拒答；需要实时事实就调用权威工具；私有知识用 RAG并强制引用；微调用于行为和格式，不适合频繁更新事实。Agent还要严格工具 schema、参数验证、权限、读后写确认、状态机和结果验收，禁止模型伪造工具成功。用事实性、引用支持、工具正确率和任务成功率评测，低置信或证据不足时澄清/拒答/人工，而不是用另一个模型一句‘看起来正确’兜底。”

### 预训练 / SFT / RLHF / DPO 的区别与目的？什么场景选择微调而不是 RAG？LoRA / QLoRA 原理、一般加在哪些模块、秩取多少？GRPO 与 PPO 核心区别？RLHF 中 reward model / Actor / Critic / Reference Model 分别做什么、为什么要 KL 约束？对齐税怎么减少、微调后能力退化怎么防止？PEFT 有哪些方法？

> “预训练学习通用语言分布；SFT用示范数据教任务和格式；RLHF用人类偏好训练 reward model再优化策略，DPO直接从偏好对优化、实现更简单。RAG适合更新/私有事实，微调适合稳定改变行为、风格、领域表达或让小模型学任务。LoRA冻结基座，只给线性层加入低秩增量，常放注意力 Q/K/V/O和有时 MLP；rank按数据和评测选，不背固定值，QLoRA再量化基座省显存。PPO有 Actor、Critic、Reward和 Reference，KL限制偏离基座；GRPO用组内相对奖励估计优势，通常不依赖单独 Critic。防能力退化靠高质量混合数据、较小学习率、正则/KL、回归评测和可回滚 adapter。PEFT还包括 adapters、prefix/prompt tuning、IA3等。”

### 分布式训练常见模型并行方式、ZeRO-1/2/3 区别？训练数据集怎么构建、学习率高低怎么判断？

> “分布式训练可组合数据并行、张量并行、流水线并行、专家并行和序列/上下文并行。ZeRO-1切分 optimizer states，ZeRO-2再切分 gradients，ZeRO-3连 parameters也切分，显存逐级下降但通信与实现复杂度上升。数据集要定义任务、许可与隐私，去重清洗、质量/难度分层、训练验证测试防泄漏并记录 lineage。学习率过高常见 loss震荡/发散、梯度异常和能力遗忘，过低则收敛慢或欠拟合；用 warmup、曲线、梯度范数、验证集和小规模 sweep判断，不能只看训练 loss。”

### 大模型多模态？大模型 Markdown 转 HTML？长上下文模型的注意力稀释（lost in the middle）、标称上下文用到 60-70% 就开始下降？

> “多模态模型把图像、音频或视频经各自 encoder/patch/token表示对齐到语言模型空间，并可生成文本或其他模态。Markdown转 HTML应使用成熟解析器并做白名单净化、链接协议限制和代码高亮隔离，不能直接信任模型输出。长上下文存在 lost-in-the-middle、噪声竞争和位置外推问题，标称窗口只是容量上限，不保证每个位置同等有效。‘用到60～70%就下降’不是通用定律，应在目标模型、任务和位置分布上做 needle/多证据及真实业务评测，优先检索和压缩而非盲塞满窗口。”

### KV cache 原理和作用？推理时延怎么优化（Continuous batching / PagedAttention / Speculative decoding / 量化 / 蒸馏）？模型剪枝与量化原理？如何优化长文本生成显存占用？

> “自回归生成时，每一步历史 token的 K/V不变，KV cache保存它们，避免重复前向计算；代价是显存随层数、序列、batch和 KV头增长。Continuous batching动态把请求加入批次，PagedAttention分页管理 KV减少碎片，speculative decoding让小模型草拟、大模型并行验证；量化降低权重/KV精度和显存，蒸馏训练小模型，剪枝删除低贡献结构。长文本可用 GQA/MQA、KV量化/淘汰、滑动窗口、分块注意力、prompt缓存和限制并发，必须同时观察首 token、每 token时延、吞吐与质量损失。”

### Prompt 是什么、可维护的 Prompt 通常包含哪些部分？Prompt 工程见解、常见结构、多阶段 Prompt 策略？Prompt Injection 与越狱区别、RAG 如何防御间接提示词注入、前端如何防止提示词注入？

> “可维护 Prompt包含角色/目标、可信输入边界、上下文、约束、工具规则、输出 schema、少量高价值示例和失败/拒答策略，并像代码一样版本化、模板化和评测。复杂任务拆为分类、检索/规划、生成、验证多阶段，每阶段输入输出结构化。Prompt Injection利用不可信内容诱导模型覆盖指令，越狱更侧重绕过安全策略；RAG文档和网页内容都按数据隔离，不能执行其中指令。防线是最小工具权限、服务端鉴权、来源标记、内容扫描、结构化参数、出网/写入沙箱和人工确认，前端只能做展示与确认层，不能单独解决。”

### 项目中为什么选择 MLP 而不是 Transformer / LSTM（各自适用场景与模型容量取舍）？

> “如果输入是固定长度的结构化特征、样本和延迟预算有限、长程依赖不重要，MLP参数少、训练部署简单，可能比 Transformer更合适；LSTM适合序列并以递归状态建模，但并行性较差；Transformer用注意力处理全局依赖和并行训练，容量大但数据、计算和内存成本高。选型要用最小满足需求的模型，在同一数据划分比较质量、P95延迟、吞吐、模型大小和维护成本。项目回答必须给真实输入结构和基线结果，不能用‘Transformer太重’一句话代替实验。”

### 大模型的 Token 是如何切分（分词）的？为什么 strawberry 这类词在部分模型中会被拆成多个 Token（BPE / 子词粒度）？

> “Tokenizer通常先规范化文本，再用 BPE、WordPiece、Unigram或字节级方案把字符串切成词表中的子词并映射 ID。BPE从基础符号开始反复合并训练语料中高频相邻对，所以常见词可能一个 token，生僻词会拆成多个。`strawberry`在某些词表里可能是整体，也可能拆成 `straw`、`berry`或更细单元；模型生成的是 token概率，并不直接数人类看到的字母。实际 token数必须用目标模型对应 tokenizer计算。”

### 为什么大模型以 Token 而不是字符或完整单词作为基本处理单位（与模型建模、词表、跨语言的关系）？

> “完整单词词表会巨大且无法处理新词、拼写和形态变化；逐字符/字节序列又太长，增加训练和推理成本。子词 token在词表规模、序列长度和开放词汇之间折中：常见片段复用，未知词仍能拆解，字节级方案还能覆盖任意语言和符号。代价是不同语言的 token效率不均、字符计数不直观，因此成本、截断和 UI流式都应按模型 token与用户可见字符分别处理。”

### 上下文窗口是不是越大越好？它对显存占用、推理延迟、调用成本和模型效果分别有什么影响（长上下文的注意力稀释、性价比权衡）？

> “更大窗口提高一次输入容量，但注意力和 KV cache让显存、首 token延迟及费用上升，具体复杂度取决于模型实现；更多无关内容还会造成注意力稀释和 lost-in-the-middle，效果不一定提高。工程上我先用检索、结构化状态、摘要和缓存只放必要证据，并为输出、工具 schema预留预算；只有任务确实需要跨长文档整体关系时才使用大窗口。选型看目标数据上的准确率、引用、P95、吞吐和单位成功成本，不把标称窗口当质量排名。”

## 工程落地与业务

### AI 辅助开发的完整工作流？真实使用场景？如何在项目中使用 AI 工具来提升效率？平时用什么 AI 工具（Cursor / Trae / Codex / 文心 / DeepSeek 等）、不同模型区别与适用场景、为什么用 Cursor？

> “我的 AI辅助流程是先写需求、接口、约束和验收，再让工具读取最小相关上下文，生成计划或小步补丁；我逐行审查，运行格式、类型、单元、集成和安全检查，最后用真实场景验收并记录失败案例。适合检索代码、脚手架、测试候选、迁移和日志分析，不把生产发布或敏感写操作完全交给模型。工具/模型选择看仓库理解、工具调用、上下文、延迟、隐私和成本；Cursor、Codex等只是交互载体。面试时我只讲真实使用过的工具与数据，不用品牌列表冒充能力。”

### 能力如何封装为 Skill？触发条件？意图识别是否人工干预？多 Skill 串行 / 嵌套，依赖冲突、参数不兼容的容错设计？有无编排优先级调度？Skill 版本迭代如何平滑灰度、兼容兜底、旧版下线、故障回滚？

> “把能力封成 Skill时写清触发条件、输入输出、前置权限、步骤、工具、验证与失败处理，并把脚本/模板随版本发布。路由先规则过滤再模型匹配，用户显式指定优先；低置信或高风险要澄清/确认。多 Skill通过 DAG声明依赖、版本与 schema，调度器做拓扑排序、参数适配、幂等、超时和补偿，禁止隐式递归。版本用语义化与兼容契约，按租户/流量灰度，双跑比较 eval；旧版保留观察期，故障切回稳定版。人工负责能力边界和门禁，模型只在允许候选中编排。”

### 流式输出怎么实现（SSE/WebSocket、服务端 yield、前端增量渲染；处理中断 / 重连 / 超时）？用户点击停止生成后端如何立即终止？多轮对话 + 流式输出如何保证消息不乱序？跨服务流式透传？流式场景内容安全实时截断（敏感词立即停流）？

> “文本流常用 SSE/HTTP stream，双向音频用 WebSocket/WebRTC。服务端把模型增量转为带 eventId、messageId、sequence的事件并 flush，前端增量解码、缓冲后按帧渲染；断线携带游标续传，无法恢复就标 interrupted。停止生成时前端 Abort并发送 generationId，后端把取消传播到模型、工具和跨服务流。消息用父子 ID和序号去重保序，跨服务采用支持背压/取消的流式协议。安全检测分输入、增量窗口和最终输出三层，命中高风险立即停止下游、发送明确终止事件并审计，不能只在前端隐藏。”

### 解决大模型输出快慢对 RAF 的优劣势、如何结合 nextTick 优化流式渲染？如何解决 Markdown 渲染抖动、增量渲染能否解决？大模型输出内容格式不对前端无法渲染怎么兜底？前端从前端角度如何防止提示词注入？

> “模型很快时每 token更新会造成过多响应式渲染，rAF合并到每帧一次最合适；模型很慢时可直接显示或用打字机平滑，但不能人为积压太久。Vue中修改响应式缓冲后，只有确需读取更新后的 DOM才 await nextTick，不能每 token都 nextTick。Markdown抖动来自未闭合语法和全量重解析，应维护增量缓冲/AST，代码围栏、表格和 HTML到安全边界再提交。解析失败退回纯文本并保留原始内容。提示注入防御仍靠后端权限与工具护栏，前端负责标识不可信来源、敏感动作确认和安全渲染。”

### 大模型输出的数据如何渲染成对应组件？前端如何通过接口拿到 JS 代码并在前端渲染 / 执行？AI 返回的 ECharts 图表报错了怎么办？

> “我不会让模型直接决定任意组件或执行任意 JS。让它输出版本化 UI schema，例如 `{type:'chart', props, dataRef}`，服务端做 JSON Schema与权限校验，前端只从白名单组件注册表映射并对 props设上限。确需运行代码时放独立 origin的 sandboxed iframe或受限 Worker，禁网络/存储/宿主 API，设 CPU/内存/超时和消息协议，绝不能 eval到主页面。ECharts option也做 schema、数据量、formatter函数和 URL过滤；渲染异常由错误边界捕获，显示表格/JSON降级并把 option、模型版本和 trace上报。”

### 多模型路由：自动降级、流量灰度、负载均衡、故障隔离调度架构？Agent 批量任务并发（动态限流、优先级调度、故障隔离防雪崩）？Agent 上下文超长引发卡顿超时，前后端协同做裁剪、缓存复用、分片请求、增量渲染？

> “模型网关先按能力、地区和合规筛选，再按实时成功率、P95、负载、质量和成本路由；每供应商独立并发池、超时、熔断和 canary，故障降级到备用模型、规则/缓存或人工，防级联重试。批量 Agent任务进优先级队列，以租户配额和动态令牌桶调度，长短任务隔离、背压和幂等 checkpoint防雪崩。上下文过长时前端先传引用和增量差异，后端检索/摘要/裁剪并缓存稳定前缀；响应分片流式返回。全链路传播 deadline和取消，单位任务预算超限即停止或降级。”

### AI 工作流上线后，全链路监控、异常告警、模型幻觉导致业务出错的兜底方案？Agent 推理路径有没有落库、怎么用它做质量分析和回溯？如何评估一个 Agent 系统好坏的指标体系？

> “全链路 trace包含用户请求、路由、模型调用、检索、每次工具、重试和最终状态，记录版本、延迟、token/成本、结构化参数摘要与证据引用，敏感数据脱敏。轨迹事件不可变落库，checkpoint另存当前状态，可按 trace重放外部结果而不重复副作用。指标分任务成功/验收、工具选择和参数正确、事实与引用、拒答安全、轨迹效率、P50/P95、成本、人工接管和用户反馈。幻觉高风险动作由规则和业务系统验证、可逆执行/人工确认兜底。告警关联发布版本并有自动回滚门槛。”

### Agent 可评估性、工具调用的安全沙箱设计（模型判断 + 规则兜底双层）？Harness Engineering 怎么理解、以后会不会成为标准开发范式？

> “可评估性要在设计时把目标、状态、动作和证据结构化，使每一步能独立断言，而不是只评最终文本。工具沙箱按租户创建最小文件/网络/凭据作用域，命令和参数规则先过滤，模型判断只作为软层；限制 CPU、内存、时间、出网和写目录，高风险外部动作预览后确认，所有调用审计并可撤销。Harness Engineering是围绕 Agent搭建上下文、工具、测试、观测、权限和反馈闭环，让模型在好环境中稳定工作。我认为它会成为重要范式，但具体术语可能变化，原则类似 CI/CD和平台工程，需要用任务成功率证明价值。”

### 切换国产大模型，提示词、工具调用逻辑要改哪些点？使用什么大模型、调用成本如何管控、写一千行代码消耗多少 token / 成本多少？Token 成本问题消耗过快怎么排查（可观测、生成 LLM span 树读四类 token 用量）？

> “切换模型先做能力契约测试：system/tool角色、并行工具、JSON Schema遵循、流式事件、tokenizer、上下文、错误码和安全策略可能不同。提示词避免供应商私有语法，工具执行层统一 adapter，并用回归集、灰度和 fallback验证。成本按请求记录缓存输入、普通输入、推理/输出等供应商实际 token类别、单价和重试；‘一千行代码多少钱’没有固定答案，取决于语言、上下文、输出 token和当前价格，必须用 tokenizer和账单估算。消耗异常时看 LLM span树，分 system/tool schema、检索/历史输入、缓存命中和输出，定位重复上下文、循环或失败重试。”

### 海量积压场景，消息队列（RabbitMQ 死信 / 延迟队列）怎么保障消费稳定性？双十一场景：大量用户询问优惠 / 退换货，如何设计 Agent 应对高并发稳定性与成本控制（意图分层、核心路径缓存、降级限流、成本实时追踪）？Agent Demo 改造成双十一级别生产系统最大架构挑战？

> “积压时队列要有持久化、确认、消费者并发和预取上限、幂等、退避重试、DLQ、优先级与可审计重放；先保护依赖，再扩容，不能让失败消息热循环。双十一咨询先用规则/小模型做意图和风险分层，优惠规则/订单/退货走权威 API或确定性流程，FAQ缓存，复杂长尾才用大模型；租户限流、排队、超时、熔断、降级模板和人工通道保证核心路径。实时追踪每意图成功率、P95和单位解决成本。Demo到生产最大挑战通常不是模型调用，而是身份权限、峰值容量、数据一致、评测、可观测与故障恢复。”

### AI 会替代前端吗？有了 AI 还回得去"古法编程"吗？前端如何与 AI 结合提升自己的不可替代性？AI 时代前端扮演的角色、学习路线、未来是否还有前端岗位？前端除了页面还能用来干什么？

> “AI会减少重复页面和样板代码，但产品理解、交互质量、浏览器系统、性能、安全、可访问性和线上责任仍需要工程判断。前端也不仅是页面：它连接多模态输入、实时流、可视化、桌面/跨端、本地推理和 Agent的人机协作。我的路线是继续打牢 JS/TS、浏览器、网络和测试，同时掌握流式 UI、结构化生成、RAG引用、工具审批、评测和安全。AI生成后我仍能脱离工具定位和修复，这不是回到‘古法’，而是保留验证能力；不可替代性来自能定义问题并对结果负责，不是手敲代码速度。”

### Coding Agent 项目是什么、为什么要做？跨轮次意图跳跃如何结合上下文判断当前意图？长时间编程任务超出上下文窗口采用什么压缩机制（参考 Claude Code）？AI 编程工具（Claude Code / Codex）架构？AI coding 辅助程度、生成代码占比？是否沉淀项目专属知识库 / 错误案例给 AI？测试 Agent 怎么实现？不同 AI 编程工具的规则 / 上下文 / 长期记忆如何共享？

> “Coding Agent把自然语言目标转为持续的代码检索、计划、修改、命令/测试和复盘循环，价值是跨文件长任务，而不只是补全。跨轮意图用当前明确指令优先，结合活动任务状态判断是追加、纠正还是新任务，冲突时澄清。长任务把稳定规则、计划/checkpoint、变更摘要、失败证据和最近上下文保留，文件内容按需重新检索，避免保存整段历史。典型架构包含上下文组装、模型、文件/终端工具、沙箱、diff、审批、测试和 trace。代码占比不重要；项目规则版本化，错误案例变回归 eval，测试 Agent基于规格生成/运行/变异验证。跨工具共享用仓库规则、标准文档和可导出的记忆，而非绑定私有隐式状态。”

### 视频理解 / 视频剪辑 Agent 从输入到成片全流程与模块？任务状态机六大状态与流转、指数退避重试、熔断、音画同步检测、字幕完整性校验？长视频转写调用什么模型、处理时长、分片上传断点续传、能否跨视频检索？

> “视频 Agent链路是分片上传与校验、转码/抽帧、ASR与说话人、镜头/对象/音频理解、素材索引、脚本规划、时间线编辑、渲染和质检。状态可设 queued、running、retrying、waiting_review、succeeded、failed/cancelled，事件带版本和 checkpoint；可恢复错误指数退避，连续故障熔断。质检比较时间线、音频峰值和字幕时间戳，检测黑帧、静音、音画漂移、字幕覆盖率。长视频按静音/场景分片并保留 overlap与绝对时间，上传用 multipart续传。跨视频检索对字幕、镜头 caption和视觉/音频 embedding建权限索引；模型、时长和准确率只报真实测试数据。”

### 在前端 / Node.js 端用 ONNX Runtime 部署模型遇到过哪些问题（模型格式转换、推理 session 反复创建导致的内存泄漏），如何预防内存泄漏风险、做推理资源复用？

> “ONNX部署先处理算子支持、动态 shape、opset、预后处理一致和数值精度，分别在转换前后用固定样本对齐输出。前端 onnxruntime-web根据设备选择 WASM或 WebGPU，模型大时做分片、缓存和 Worker。最大的资源坑是每次推理创建 session、tensor或绑定却不释放；我用按模型版本的 session单例/池，限制并发，显式 dispose可释放对象，组件卸载取消任务，并监控 heap/GPU内存。模型切换采用引用计数和空闲回收，失败时清理半初始化资源，不能只等 GC处理原生/WASM内存。”

### 用大模型提升推荐效率（如新闻推荐）的业务思路？意图识别模块如何实现？知识库如何构建、是否用 ReAct 模式？

> “推荐系统可让大模型理解新闻语义和用户自然语言意图、生成标签/embedding、解释或重排候选，但候选召回、实时特征、去重、多样性和业务约束仍由推荐系统负责，避免用 LLM逐条生成造成成本和不稳定。意图识别先用规则/小分类器处理高频确定类，低置信再用 LLM结构化分类并可追问。知识库按新闻时效、来源、实体、权限增量索引。只有需要多步查用户偏好、新闻事实和工具并根据观察调整时用 ReAct；普通推荐请求用固定召回—排序 Workflow更可控。”

### 如果让你设计一个 AI Agent 工作流可视化编辑器，你觉得应该怎么设计（节点与连线的数据结构、编排与执行引擎、变量传递、调试 / 回放与异常态展示）？

> “编辑器数据用规范化图：nodes保存 id、type、version、config和 UI位置，edges保存 source/target/port与条件；变量用带类型的引用而非字符串插值。保存时做 schema、端口类型、必填、环和权限校验，编译成执行 DAG/状态机；循环节点必须显式且有上限。运行引擎负责拓扑调度、并发、幂等、重试、checkpoint、取消和人工节点。调试界面展示每节点 queued/running/succeeded/failed、输入输出摘要、token/成本、耗时和 trace，可从某 checkpoint用冻结的上游结果回放，外部副作用默认不重放。版本、迁移、灰度和秘密引用也属于一等能力。”

### 大模型流式返回 JSON 时，前端如何做增量解析（处理未接收完整的 JSON 片段、避免半截 JSON 解析报错、错误容错与重试）？

> 我会先按 SSE/NDJSON 的帧边界消费，而不是每收到一个 token 就 JSON.parse。网络层维护字符串缓冲区，只切出已经完整的事件；事件里的结构化参数再用增量状态机记录字符串、转义符、括号深度，只有闭合后才解析。界面先展示可确定的文本，未闭合片段保持在缓冲区。每帧带 requestId、sequence 和 done，重复帧按序号去重，缺帧或格式错误进入可恢复错误态。重试时携带幂等键和已确认序号，从最近检查点续传；连续失败则停止解析、保留原始片段并允许用户重新生成。

### 前端如何和算法 / 模型团队约定流式接口、错误码与数据结构（前后端协议对齐、字段命名与版本兼容）？

> 我会先定义版本化事件信封，例如 `{version, requestId, sequence, type, data, error, done}`，再用 OpenAPI/JSON Schema 固化每种事件的数据结构。字段命名、时间格式、空值、枚举和错误码必须有单一规范；错误区分可重试、不可重试、限流、内容安全和上游失败。新增字段保持向后兼容，删除或改语义必须升主版本。前端、网关和模型服务共同跑契约测试与录制样例，灰度阶段同时监控未知事件、解析失败率、乱序和断流，避免只靠口头约定。

### 浏览器端运行小模型（端侧推理）的价值与限制是什么（相较云端调用，在延迟 / 隐私 / 包体体积 / 能力边界上的权衡）？

> 端侧推理适合低延迟、离线和隐私敏感的小任务，例如分类、向量化、轻量改写与本地搜索；数据不出设备，也能减少云端调用成本。限制是模型下载会增加首包和缓存，WebGPU/WASM 的设备兼容、显存、发热和耗电差异很大，模型能力与上下文长度也弱于云端。工程上应按设备能力懒加载量化模型，显示下载进度，限制并发并提供云端降级；敏感数据是否允许降级上传必须由用户选择。大型生成、复杂工具调用和高质量推理仍优先放在云端。

### 流式聊天场景下，如何优化长文本输出的展示与交互体验（如大量增量内容渲染卡顿、滚动位置保持、长文可读性与不阻塞主线程）？

先区分四层：网络字节解码、SSE/NDJSON 事件组装、消息内容缓冲、视图渲染。chunk 不等于一个 token 或完整事件；按协议解析后再累加，并将 Markdown 解析与 DOM 更新合并到每帧一次或固定短周期。只解析当前变化的消息，已完成的历史消息保持稳定；非常长的会话再考虑按消息虚拟化，保留复制全文与查找入口。

```js
function createFrameWriter(render) {
  let text = '', frame = null
  const flush = () => {
    if (frame !== null) cancelAnimationFrame(frame)
    frame = null
    render(text)
  }
  return {
    append(delta) {
      text += delta
      if (frame === null) frame = requestAnimationFrame(flush)
    },
    flush,
    dispose() { if (frame !== null) cancelAnimationFrame(frame); frame = null },
  }
}
```

示例的 render 仍需检查 conversationId/generationId 归属。完成和保留部分结果的失败分支主动 flush，离开页面 dispose；后台页可能暂停 rAF，不能只靠下一帧保证尾段显示。[MDN requestAnimationFrame](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame)。

用户接近底部时才自动跟随；上翻阅读后保持位置并显示“新内容/回到底部”。代码块横向滚动、合理行宽、段落间距和停止/重试入口比逐字动画更重要。重解析可移至 Worker，DOM 仍在主线程；任何 HTML 渲染仍需清洗，部分代码围栏不能绕过安全处理。用长回复、低速设备和中途切换会话测帧耗时、解析次数与尾段完整性。
