# Agent 工程与场景标准问答

这一组题对应 Agent 岗二面常见的系统设计和项目拷打。回答原则是：先明确业务目标和风险，再画确定性控制面与模型决策面，最后补失败路径、评测和灰度。

> VueChest 当前的 AI Chat 已具备模型中转、流式 UI、会话持久化和取消能力，但从现有代码看，它不是一个完整 Agent。面试时可以把它作为 AI 应用前端经验，不要声称已实现工具循环、RAG、长期记忆或多 Agent；这些应通过真实新增项目或实验补齐后再写入简历。

---

## 一、项目介绍与架构设计

### Q1：请介绍一个 Agent 项目。

> “项目解决的是【用户/业务问题】，原来的方式在【质量、效率或成本】上存在【有数据的痛点】。我没有一开始就上 Agent，而是先验证单次 LLM / RAG / 固定 Workflow 基线；因为任务需要【根据中间结果动态选工具或规划】，所以最终把【局部节点】设计成 Agent。
>
> 架构上，入口层负责鉴权和会话；orchestrator 管状态、预算和中断恢复；模型层做路由与结构化决策；工具执行器负责 schema、权限、幂等和超时；知识层提供【检索】；观测层记录完整 trace。我的个人职责是【具体模块】，最难的问题是【真实失败】，我通过【方案】解决，并用【评测集和线上指标】验证为【真实结果】。目前边界是【不足】，下一步会【改进】。”

**面试官想听到的证据：**

- 为什么必须用 Agent，而不是普通工作流。
- 一次任务的真实 Trace，而不是框架名列表。
- 失败样本和修复前后评测。
- 个人代码、设计和决策边界。

### Q2：请设计一个企业知识助手。

> “我会先确认用户、数据权限、问题类型、时延和错误成本。第一版优先做带引用的 RAG 问答，而不是自主 Agent：文档接入后解析、结构化切分、按租户建索引；在线做权限过滤、混合召回、重排、生成和引用校验，无证据时拒答。
>
> 只有当需求包含创建工单、查询业务系统、汇总多来源并继续行动时，才在外层增加受限 Agent。控制面保存状态、步数和预算，工具执行器做用户授权与审计，高风险写操作必须预览和确认。上线前按部门构造评测集，分别验证检索、答案、权限隔离和提示注入，再小流量灰度。”

### Q3：请设计一个能预订会议的 Agent。

> “我会把自然语言理解与最终写操作分开。Agent 先提取参与人、时间范围、时区、时长和会议方式；缺失信息先澄清。然后并行调用只读日历查询，计算候选时间，展示给用户选择。用户确认后才调用创建会议工具，并使用幂等键防重复创建。
>
> 如果参会人很多，可以把空闲时间查询并行化，但最终写入由单一协调器串行提交。遇到权限不足、时区歧义、会议室冲突或部分参与人不可见时，返回可解释的替代方案。任务成功以日历服务返回的事件 ID 和二次读取状态为准，不以模型说‘已创建’为准。”

### Q4：单 Agent 和多 Agent 如何做选型实验？

> “先用同一任务集建立单 Agent 基线，再设计只有在上下文隔离、专业分工或并行性上有明确收益的多 Agent 版本。两边使用相同工具和模型预算，比较任务成功率、P95 延迟、token、工具调用数、恢复率和人工介入率。
>
> 多 Agent 如果只是把同一问题重复问几个角色，质量提升可能来自更多 token，而不是架构本身。因此还要做等成本对照。只有它在关键任务切片上的质量收益稳定覆盖协调成本，才进入生产。”

## 二、状态、可靠性与执行安全

### Q5：Agent 的状态应该保存什么？

> “我会区分事实状态和对话文本。事实状态包括 task ID、目标、约束、当前节点、已完成步骤、工具调用及结果引用、预算、待审批动作和产物位置；对话只是输入来源之一。状态对象要有 schema 版本和 revision，写入采用乐观锁或事务。
>
> Checkpoint 放在有副作用前后、人工等待前和长步骤完成后。恢复时不直接重放所有动作，而是读取最新 checkpoint，校验外部世界是否变化，并根据幂等记录决定继续、补偿或重新规划。”

### Q6：模型或工具超时后怎样重试？

> “先分类错误：限流、网络抖动和临时 5xx 可重试；参数非法、权限不足和业务拒绝不应原样重试；模型输出校验失败可以做一次带错误信息的修复。所有重试有上限、指数退避和 jitter，并受总任务 deadline 约束。
>
> 只读调用通常安全重试；写调用必须有幂等键、查询提交状态或补偿动作。若请求超时但服务端可能已成功，先按幂等键查询，不能直接再写一次。连续失败触发熔断、备用模型或降级到人工，不让 Agent 自己无限尝试。”

### Q7：如何处理 Agent 执行中断和恢复？

> “orchestrator 每个关键节点持久化 checkpoint 和事件日志，工具调用记录 `planned/running/succeeded/failed/unknown` 状态。进程重启后按 task ID 取最后状态；如果工具结果确定成功就继续，如果明确失败按策略重试，如果状态 unknown 则先查询外部系统或人工确认。
>
> Prompt、模型、工具 schema 和代码版本也要随 checkpoint 保存，否则恢复时行为可能漂移。用户取消会传播 AbortSignal，但已发出的外部副作用需要工具自己的取消或补偿语义。”

### Q8：高风险 Agent 为什么需要两阶段执行？

> “模型先生成意图不直接提交。第一阶段调用只读工具得到 preview，包括目标对象、金额、收件人或影响范围；确定性策略引擎检查权限、限额和合规；用户看到关键信息并确认后，第二阶段才使用一次性 approval token 提交。
>
> token 要绑定用户、动作摘要、资源版本和过期时间，防止确认后参数被替换。提交使用幂等键并写不可变审计记录。这样即使模型被注入，也无法绕开宿主的授权与确认。”

### Q9：跨境汇款场景下，Agent 超时或失败如何保证资金安全？

> “Agent 只能负责收集信息、解释规则和提出转账意图，账务状态机必须由确定性交易服务控制。模型不能直接修改余额。正式提交前做 KYC/AML、账户、币种、汇率有效期、限额和制裁名单校验，并要求用户确认最终金额和收款人。
>
> 提交使用全局幂等键和事务 outbox。超时后先查交易状态：成功则返回凭证，失败才允许安全重试，unknown 进入人工或对账，不做重复扣款。资金流采用不可变账本和补偿交易，而不是直接改旧记录。Agent 故障时降级到传统表单和客服，安全优先于自动完成率。”

### Q10：怎样限制 Agent 的工具权限？

> “权限在每次调用时基于当前用户重新计算，不能只在会话开始判断。工具拿短期、最小范围、不可转移的凭据，模型只看到逻辑资源 ID，不看到密钥。不同 Agent 或工具运行在隔离执行域，文件、网络和数据库各自白名单。
>
> 我会把 read、draft、execute 分成不同 capability；默认拒绝未声明能力；高风险工具只能由满足策略的状态节点调用。所有拒绝也记录原因，评测中专门加入越权、跨租户和间接注入用例。”

## 三、Prompt、模型与上下文工程

### Q11：生产 Prompt 如何组织和版本化？

> “我会把稳定策略、任务说明、动态上下文和输出契约分层。通用安全策略放最高优先级；工具的使用时机和参数约束尽量写在工具描述；用户数据和检索内容明确标记为不可信数据；输出使用 schema。
>
> Prompt 存模板 ID、版本、变量 schema 和变更说明，进入代码评审。每次变更在固定评测集和历史失败集上跑回归，线上按版本打 trace 并小流量灰度。Prompt 不是散落在业务代码里的字符串，也不能只凭几次手工对话判断效果。”

### Q12：模型怎样路由和降级？

> “我先按任务难度、模态、工具能力、上下文长度、SLA 和数据政策筛模型。简单分类、改写可用小模型；复杂规划或最终合成用强模型；确定性任务直接用代码。路由器要有静态规则兜底，不应完全依赖另一个昂贵模型。
>
> 降级顺序由业务定义：同能力备用模型、减少上下文或关闭非关键步骤、切到固定 Workflow、最后人工处理。模型切换不是只改名称，因为 schema、工具调用、采样和 Prompt 行为可能不同，必须分别评测。”

### Q13：如何管理大量工具而不把 schema 全塞进 Prompt？

> “先按用户权限和当前工作流做静态过滤，再用关键词、embedding 或轻量分类器检索少量候选工具；必要时先给 namespace 或工具目录，让模型再展开具体 schema。缓存稳定工具前缀，并保持工具列表顺序稳定。
>
> 路由层本身要评测 top-k recall，确保正确工具没有在第一层被丢掉。高频核心工具可以常驻，长尾工具按需加载。描述重复或边界重叠时应重构工具，而不是只期待模型更聪明。”

### Q14：如何减少长对话中的上下文污染？

> “把当前有效目标、约束和事实放结构化状态，不把所有历史原样重放。对话按阶段摘要，工具结果只保留必要字段和原始结果引用；已撤销的指令显式标记失效；检索内容带来源、时间和可信级别。
>
> 每轮构建上下文时重新按优先级选择，而不是无限 append。遇到目标切换可新建子任务或会话。评测中加入长对话、冲突指令和旧信息干扰用例，观察模型是否仍遵守最新已确认状态。”

## 四、评测、可观测与上线

### Q15：没有历史数据时，怎样建立第一版 Agent 评测集？

> “先从产品需求和风险分析构造 30～100 条小而有代表性的任务，覆盖正常、边界、工具失败、权限、拒答和攻击样例。每条定义初始环境、允许工具、成功条件、禁止行为和最多预算，避免只有一个参考文本答案。
>
> 由领域专家审一轮，再让不同实现跑出轨迹，暴露 rubric 歧义。上线后把人工接管、用户差评、长循环和工具错误脱敏回流，并按任务类型分层抽样，防止评测集只剩容易题。”

### Q16：LLM-as-Judge 怎么避免不可靠？

> “优先用确定性检查：schema、数据库状态、测试结果和权限规则。语义质量才使用 Judge。Rubric 拆成单一维度并给正反例，随机交换候选顺序，隐藏模型身份；部分样本由多 Judge 或人工复核。
>
> 在一批人工金标上计算一致性，定期重校准。Judge 分数适合做回归和相对比较，不应伪装成绝对真理；涉及安全违规时，低频严重错误必须单独统计，不能被平均分稀释。”

### Q17：怎样灰度一个新的模型或 Agent 版本？

> “先离线回归，确认任务成功、安全、延迟和成本没有越过门槛；再 shadow 真实流量，只执行无副作用的决策或使用 sandbox，对比旧版本；随后从内部用户和低风险小流量开始 canary。
>
> 版本维度包括模型快照、Prompt、工具 schema、检索索引和编排代码。设置成功率、P95、费用、高风险违规和人工介入等自动回滚阈值。写操作灰度必须保证版本间幂等和状态兼容，不能只回滚模型而留下不可恢复中间状态。”

### Q18：线上成功率下降，你怎样排查？

> “先按版本、任务类型、租户、模型和工具切片，确认是整体还是局部；再沿 trace 看入口理解、检索、模型决策、工具执行、状态更新和最终验收哪一层首先异常。同步检查模型/Prompt/工具 schema/索引/依赖服务是否变更。
>
> 如果影响持续，先回滚或关闭问题能力，再从失败样本最小复现。修复后把样本加入回归集，并补告警或契约测试。没有可复现 trace 时，第一优先级是补观测，不靠反复改 Prompt 猜原因。”

### Q19：怎么向面试官说明项目指标？

> “我会报告完整口径，例如‘在 200 条经过领域专家标注的任务集上，端到端成功率从 A 到 B；P95 从 C 到 D；单成功任务成本从 E 到 F’，并说明模型版本、重复运行次数和置信区间或波动。
>
> RAG 还要拆检索 recall 和答案 faithfulness，Agent 拆工具参数正确率、平均有效步骤与人工介入。若项目未上线，我明确说是离线指标；若没有测过，就不编数据，而是说明现在缺什么和怎样补。”

## 五、Agent 项目最小作品建议

如果目前只有 VueChest AI Chat，可以新增一个小而完整的 Agent 实验，再把它写进简历。建议范围控制在两周可完成：

### 题库学习 Agent

**用户目标：** 根据薄弱点制定复习计划、抽题、判分并更新错题。

**最小能力：**

1. `search_questions(topic, difficulty)`：只读检索题库。
2. `submit_answer(questionId, answer)`：记录原始回答。
3. `grade_answer(...)`：用 rubric 给分，并保存 Judge 依据。
4. `update_review_plan(...)`：先预览，用户确认后写入计划。
5. 状态图：选题 → 作答 → 规则/模型评分 → 反馈 → 更新计划 → 结束。

**必须做的工程项：**

- 工具 schema 和运行时校验。
- 最大步骤、超时、取消与 checkpoint。
- 30 条评测集，包含答非所问、部分正确、提示注入和工具失败。
- Trace 展示每步耗时、token、工具和验收结果。
- 计划更新使用幂等键，写操作前展示 preview。

完成这些后，才可以在简历中诚实写“实现了受控 Agent 循环、工具调用、评测与可观测”，并能用真实代码接住追问。
