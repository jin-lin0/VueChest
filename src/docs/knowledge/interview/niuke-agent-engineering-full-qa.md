# 牛客全量标准答案 · 九、Agent 应用开发（不限技术栈：后端 / TS / 全栈）

## Agent 服务架构与工程

### 多 Agent 平台怎么搭建（举一个实际例子，说明各子 Agent 的职责与协作方式）？

> “例如客服平台用一个 Supervisor接收目标并维护工单状态，订单 Agent只读订单/物流，知识 Agent做带权限 RAG，政策 Agent检查退款规则，执行 Agent在用户确认后调用退款工具，质检 Agent验证答案和引用。Supervisor按意图和风险分发，子 Agent收到最小上下文和结构化 schema，返回结论、证据、置信和状态；共享事实写版本化 state，不互相复制整段对话。高风险动作由规则和人工审批，失败按类型重试或降级。是否拆多 Agent取决于权限隔离、并行性和独立评测收益。”

### 怎么理解 Harness（Agent 基础设施层），它与 Agent 核心推理逻辑的职责边界是什么？

> “Agent核心推理负责理解目标、选择下一动作和生成结果；Harness是让这段不确定推理可安全生产运行的基础设施，包括上下文组装、工具注册、状态/checkpoint、超时/预算/循环检测、并发、沙箱、审批、trace、评测和版本。核心逻辑可以替换模型或策略，Harness仍保证同样的权限与生命周期。边界原则是：模型可以建议，Harness决定能否执行；业务不可违反的约束、外部副作用和可恢复性不能只写在 prompt里。”

### 多 Agent 并发有什么性能问题，平时怎么控制 Agent 的并发量（限流 / 排队 / 异步）？

> “多 Agent会放大模型 QPS、token成本、下游连接和共享状态竞争，还可能出现扇出风暴。入口按租户/用户做令牌桶和总预算，任务进优先级队列；调度器分别限制全局、模型、工具和任务内 fan-out，并根据429、P95和队列深度动态收缩。可并行的只读任务用异步 worker，关键写操作串行或乐观锁；设置 deadline、取消传播、背压、幂等和熔断。监控并发使用率、排队时间、单位成功成本，而不是把线程/Promise开得越多越好。”

### Planner / Executor / Critic 在 Agent 中分别负责什么；Critic 是什么、为什么有时不用纯 ReAct 而要加 Critic 节点？

> “Planner把目标拆为有依赖和验收条件的步骤，Executor按权限调用工具并记录观察，Critic对中间或最终结果按 rubric、证据和业务断言检查，失败则给结构化修正建议。纯 ReAct适合短、反馈明确的任务；长任务或高风险输出可能局部合理但整体漏项，独立 Critic能做覆盖、合规和一致性检查。但 Critic也会增加延迟、token并可能自信地误判，所以只放在关键节点，结合确定性校验，最好使用不同提示/模型或人工抽检并单独评测。”

### 模型聚合网关（LLM Gateway）怎么设计，多个厂商大模型如何抽象（统一 schema + 适配器适配差异）？

> “LLM Gateway对上暴露统一 request/response、流事件、tool call、usage和错误 schema，对下每家用 adapter映射角色、参数、JSON Schema、并行工具、tokenizer和错误码。能力矩阵记录上下文、模态、地区、数据策略和健康度，路由器按任务质量、成本、延迟和配额选模型；还提供鉴权、租户限流、prompt缓存、重试/熔断、内容安全、trace和账单。统一层只抽公共语义，厂商独有能力通过 capability和扩展字段显式暴露，避免最低公分母或静默丢参数。”

### 模型调用失败时（按错误码分类）怎么处理，厂商限流怎么处理（冷却 / 排队 / 退避）？

> “我先把失败归类：400/schema不重试而修请求；401/403停止并刷新配置或告警；404模型/版本配置问题；429读取 Retry-After、进入厂商级冷却并排队/切备用；5xx、网络和超时只对幂等调用做有限指数退避加抖动；内容安全和业务拒绝不换模型绕过。每次尝试共享总 deadline和成本预算，熔断器按模型/区域隔离，半开探测恢复。流式已输出后不能透明换模型续写，前端应标中断并由用户决定重试。”

### LLM 调用的 token 成本怎么统计（厂商返回消耗 / 不返回时如何用数学模型与分词器估算）？

> “优先使用厂商响应中的 usage，并按请求记录模型版本、缓存输入、普通输入、推理/输出和工具相关 token类别，再乘调用时刻的版本化价格表；流中断也要结算已使用量。厂商不返回时使用对应官方 tokenizer在调用前后估算，图片/音频按厂商规则换算，未知 tokenizer可用回归模型按字符、语言、代码比例估计并给误差区间。账单定期对账校准。成本应归因到租户、功能、trace和任务成功，不只做全局总数。”

### 长时记忆和短时记忆的底层实现方式（基于 Redis / 数据库分别怎么存）？

> “短时记忆通常在 Redis按 `tenant:conversation`保存最近消息、滚动摘要、当前计划和 checkpoint，使用有序序列、TTL和原子版本更新；大工具结果只存对象存储引用。完整事件历史和长期事实放关系/文档数据库，表中有用户、类型、内容、来源、置信、权限、版本、创建/过期时间，语义召回再建向量索引。Redis是热缓存而非唯一真相。长期写入要用户授权、去重和纠错，读取先做租户/权限过滤，删除要同时清索引与缓存。”

### 知识库 / RAG 项目试过存放多少文档，容量与规模怎么评估？

> “容量不按‘文档数’单一衡量，我会报告真实原始字节、页数/字符、解析后 chunk数、向量维度/精度、元数据与索引副本。例如估算向量原始空间约为 `chunks × dimensions × bytesPerValue`，再加 HNSW图、全文索引、元数据和复制系数。吞吐还取决于每天增量、查询 QPS、top-k、P95和租户过滤。面试时只报实际压测规模；没有万级生产数据就说明容量模型、压测方法和扩容阈值，不编造‘存了100万篇’。”

### RAG 全站数据定期同步怎么做（checksum 增量更新、定长 + overlap 分块、结构化文档分块、TopK + Rerank、轻量血缘）？

> “同步任务先抓来源清单与权限，计算稳定 documentId和内容 checksum；未变跳过，新增/变更重新解析切块，删除写 tombstone并清两类索引。普通文本可定长加少量 overlap，但标题/表格/代码按结构切并保留父块；chunk也有 hash以复用 embedding。索引用蓝绿版本，批量完成并校验计数后原子切 alias，失败可回滚。检索做 metadata过滤、BM25+向量 TopK、RRF和 rerank。轻量血缘记录 source版本→解析器版本→chunk→embedding模型→索引版本，便于定位坏数据。”

### Agent 项目技术选型：用 LangGraph 等框架还是完全自研、Master+Sub Agent 还是 Workflow，各自的适用边界与选型依据（何时该上框架、何时该自研）？

> “简单固定流程优先 Workflow或直接 SDK；路径依赖中间观察但状态不复杂，可自研小循环；需要长时运行、分支循环、checkpoint、人审和可视化状态时再选 LangGraph等运行时。Master+Sub适合权限/领域隔离、并行和独立评测，单 Agent工具集足够时不要拆。框架收益是成熟状态与生态，代价是抽象、升级和调试；自研控制强但要承担持久化、重试、观测、安全。用 PoC比较任务成功、P95、成本、可恢复和团队维护，再做可退出的适配层。”

### 首次生成链路与多轮补充（增量生成）链路的路由如何区分与实现（何时走全新生成、何时走补充链路）？

> “请求先做结构化意图判定：若没有可用 artifact/parentVersion，或用户要求重做目标/输入发生根本变化，就走首次生成，创建新 generation和完整计划；若明确是修改、扩写、修错且引用已有 artifact版本，就走增量链路，只取相关 diff、局部上下文和约束。路由结合显式词、会话状态和版本，不确定时澄清。增量输出生成 patch并做冲突检测，不能直接覆盖；两条链路共享验收、审计和回滚，指标分别统计，防止增量链路不断累积坏上下文。”

### 多个子 Agent 给出冲突结论时如何仲裁（投票 / 置信度 / 规则裁决）？什么情况下需要人工介入兜底（高风险、低置信、合规边界）？

> “先要求每个 Agent返回结论、证据引用、适用条件和校准后的置信度。事实冲突优先权威来源、权限和新鲜度规则，数值用确定性工具复算；独立同质 Agent多数投票只能降低偶然误差，不能纠正共同偏差。可用专门仲裁器看盲化结果，但其决定也要留证据。涉及资金、法律/医疗、外部发布、合规边界，或证据不足、差距小、持续冲突时转人工；界面展示冲突点和推荐选项，而不是让人重读全部轨迹。”

### Agent 多工具调用时如何做输出校验，防止工具返回无效 / 不合规结果（schema 校验 / 结果断言 / 失败重试或降级）？

> “工具返回先过传输和 JSON Schema，再过业务断言，例如状态枚举、金额范围、版本、权限、校验和与跨字段一致性；不可信文本标为数据并做注入隔离。每个结果带 toolVersion、requestId、timestamp和来源。瞬时错误在幂等前提下有限重试，脏数据不盲重试，改查权威源或转人工；降级结果必须标注能力损失。模型总结前只注入验证通过的字段，高风险写入使用读后写校验或两阶段确认，审计保存原始响应的安全引用。”

### RAG 场景下向量数据库如何做分片，海量文档下如何优化召回速度与吞吐（分片策略 / 索引类型 / 并行查询）？

> “分片优先按租户/权限域或稳定 documentId哈希，使过滤可路由且负载均匀；按时间/业务分片适合明显局部查询，但要防热点。单分片用 HNSW偏低延迟高召回，IVF/PQ偏大规模压缩，选择由 Recall@k、内存和 P95实测。查询先 metadata/路由剪枝，再并行查必要分片，在协调层合并 top-k并 rerank；设 fan-out上限、超时和部分结果标识。热点缓存、批量 embedding、读副本和索引量化提升吞吐，扩容时后台重平衡且双读校验。”

### LangChain 与 LlamaIndex 各自适合什么业务场景（何时用编排优先的 Chain 式框架、何时用索引 / 检索优先框架）？

> “LangChain适合模型、工具、prompt和 Agent/Chain编排集成丰富的应用；LlamaIndex更聚焦文档摄取、索引、检索器、query engine和 RAG数据层。若核心难点是多步工具流程，我偏 LangChain/LangGraph；若核心是异构知识与复杂检索，我会优先评估 LlamaIndex；简单场景直接 SDK加数据库更轻。两者能力有重叠且持续演进，不能按老版本标签绝对划分。我会以真实 PoC的解析质量、状态恢复、扩展性、观测、锁定和团队语言选型。”

### 并发场景下 Agent 会话（Session）如何设计（多用户并发、会话隔离、状态一致性、上下文隔离）？

> “Session键至少包含 tenantId、userId、conversationId，授权从服务端身份派生，绝不信模型参数。消息用递增 sequence或事件日志追加，状态更新带 version做 CAS；同一会话写操作可队列串行，不同会话并行。每次生成还有 generationId和 lease，重试用幂等键，晚到结果版本不符即丢弃。上下文、缓存、向量过滤和工具凭据都按租户隔离，敏感日志脱敏。短热状态放 Redis，权威历史/checkpoint落持久库，TTL、断线恢复和并发设备冲突都有明确策略。”

### Skill 的按需加载（动态加载）是怎么实现的（如何减少启动期加载所有 Skill 的开销、按需注入上下文）？

> “启动时只加载 Skill manifest：名称、简短描述、触发标签、版本、权限和资源估算；先用规则/语义索引召回少量候选，模型确认后才读取完整说明、所需参考和脚本，并按内容 hash缓存。会话上下文只注入当前阶段相关 Skill，执行结束可卸载大资源。路由先做租户权限和依赖过滤，冲突按显式用户选择、项目级优先和版本规则处理。离线 eval检查误触发/漏触发，防止动态加载节省 token却把关键护栏漏掉。”

### CoT（思维链）对 Agent 执行效果带来哪些提升，又有什么局限性（推理质量 vs token 消耗 / 延迟 / 过度思考）？

> “更充分的中间推理能提升多步分解、约束检查和工具选择，但长 CoT会增加 token、延迟和泄露风险，也可能过度思考后改坏正确答案。生产上我不依赖或记录模型私有思维链，而让它输出简洁计划、可验证子目标、工具动作和证据；简单任务直接回答，复杂任务按风险分配推理预算。效果用任务成功率和单位成功成本验证。需要审计时保存结构化决策摘要，不把冗长自然语言推理当可靠解释。”

### SFT 数据集构建有哪些要点（数据质量 / 多样性 / 指令格式 / 难例挖掘 / 配比）？

> “SFT数据先从目标能力和失败分类反推，保证示范正确、可执行、许可和隐私合规；格式与线上 system/user/tool协议一致，工具调用包含合法 schema和失败恢复。覆盖常见、长尾、拒答、边界、多语言和难负例，去重并按来源/难度分层，防训练测试污染。配比避免高频简单样本淹没关键能力，也混入通用保持数据防遗忘。先用规则和人工双重清洗，训练后按切片评测与基座对比；主动挖线上高价值 badcase，但不把未经验证的模型输出回灌。”

### 写好一个 Harness（Agent 运行时环境）必须具备哪些核心能力（工具注册与管理、上下文管理、执行控制：超时 / 最大步数 / 循环检测 / 并发控制、可观测性 Tracing、沙箱隔离）？

> “完整 Harness需要：版本化模型/Prompt；上下文预算、检索、摘要和记忆；工具注册、schema、权限、幂等、超时和结果校验；持久状态、checkpoint、取消、最大步数/token/成本、循环检测、并发和队列；文件/网络/凭据最小权限沙箱与人工审批；跨模型 adapter、fallback和熔断；全链路 tracing、usage和审计；离线/线上 eval、回放、灰度和回滚。其目标不是替模型思考，而是把不确定输出约束成可观察、可恢复、可验证的系统。”

### 多 Agent 之间如何通信？同步（直接调用 / RPC / HTTP）与异步（消息队列 / 事件总线 / 共享存储）各自的适用场景与要解决的核心问题（协议一致性 / 超时 / 幂等性）？

> “同步 RPC/HTTP适合短、强依赖、调用方必须马上得到结果的步骤，接口要有 deadline、取消、错误 schema和熔断；异步队列/事件总线适合长任务、削峰、广播和服务解耦，必须处理 at-least-once、幂等、顺序、重试与死信。共享存储适合大结果和 checkpoint，消息只传 URI、版本和 checksum。无论哪种都用版本化结构协议、taskId/correlationId/traceId、身份权限和状态机，避免 Agent用自由自然语言约定控制字段。自然语言只放解释，机器决策字段必须结构化。”

### 后端（如 Node.js）服务如何与 Python 模型服务通信（协议选型：HTTP / gRPC / 消息队列，各自的适用场景与优劣）？

> 在线同步推理优先 HTTP/JSON，开发调试简单、网关生态成熟；高吞吐、强类型和双向流场景可选 gRPC/Protobuf，但浏览器接入和运维成本更高。耗时较长、允许异步完成的生成或批处理用消息队列，Node 提交 jobId，Python 消费后把结果写回存储并发布事件。无论哪种协议都要统一 schema、超时、幂等键、traceId、重试边界和错误码；大文件走对象存储传引用，不在 RPC 中反复复制。模型服务还要有并发队列、健康检查和熔断降级。

### 从零设计一套高并发 AI 对话系统，你会怎么拆分服务（网关 / 对话服务 / 模型代理 / 召回服务等模块边界划分与职责）？

> 我会拆为接入网关、鉴权与配额、对话服务、上下文/记忆服务、检索召回、模型网关、工具执行、内容安全和异步任务系统。接入层处理限流、幂等和流式连接；对话服务维护消息顺序与状态机；模型网关统一多厂商协议、路由、重试、熔断和成本；召回服务独立扩缩容并返回可追踪引用。在线链路只保留必要同步步骤，日志、评测和摘要异步化。全链路传 traceId，按用户和模型做并发隔离，结合缓存、排队、降级模型与预算上限防止流量尖峰拖垮系统。

## Agent 应用部署与可观测

### 了解哪些进程 / 内存监控工具（如 top / htop / pmap / /proc）？线上服务出现 CPU 飙高或内存持续增长（疑似泄漏）时如何排查（火焰图 / heap dump / 逐步缩小范围）？

> “先用监控确认是单实例还是全局、与发布/流量的关系；`top/htop`看进程线程，`ps`、`pidstat`看 CPU/上下文切换，`pmap`和 `/proc/<pid>/status|smaps`看映射与 RSS，容器还看 cgroup限制。CPU高时抓多段 profile/火焰图定位热函数、GC、锁或忙循环；内存增长先区分堆、原生、mmap和缓存，再做 heap snapshot/dump按支配树和增长对象比较。用流量切片、功能开关或 canary逐步缩小，保留现场后再重启止损。不同语言用 pprof、async-profiler、Node inspector等对应工具。”

### mmap 是什么？它解决了什么问题，适合哪些文件映射或进程间通信场景（大文件读写、共享内存、零拷贝）？

> “mmap把文件或匿名内存映射到进程虚拟地址空间，访问页面时由操作系统按需 page fault载入，可利用页缓存，多个进程映射同一文件实现共享。适合大文件随机访问、只读模型权重、数据库页和 IPC，减少显式 read/write与用户态缓冲复制；但不等于所有路径都零拷贝。要处理页错误抖动、映射长度/对齐、文件截断、脏页刷盘、一致性和地址空间，顺序一次性小文件未必比普通 I/O更快。”

### writev 是什么？它如何通过聚合多个缓冲区减少系统调用开销（分散写、减少上下文切换）？

> “writev是 POSIX scatter/gather I/O：一次系统调用接收多个 iovec缓冲区，按顺序写到同一文件描述符，适合协议头、正文和尾部本来分散在内存时避免先拼成连续大缓冲，减少系统调用和一次用户态拷贝。它仍可能短写或被信号中断，返回的是总写入字节数，调用方必须推进已写过的 iovec并继续；还受 IOV_MAX限制。网络库常用它批量发送，但并不保证磁盘落盘，也不自动解决背压。”

## Agent 评测与质量保障

### Agent 任务成功率这类测试数据怎么测的（用什么指标、如何构造评测集）？

> “先把任务成功定义为可执行验收器，例如正确状态变化、文件测试通过、订单查询与权威结果一致，而不是模型自评。评测集来自真实匿名流量、历史 badcase、专家设计边界和合成变体，按意图、难度、语言、工具、风险分层并冻结版本。指标包括 end-to-end成功、pass@k、工具参数正确、无效步骤、事实/引用、安全、P95和单位成功成本；随机模型多次运行给置信区间。测试环境冻结工具结果或使用可重置沙箱，防外部波动污染结论。”

### 没有用户反馈时如何对 Agent 效果做有效抽检（采样 / 离线评测 / 自动评分）？

> “没有显式反馈不等于无法评估。我会按风险、意图、模型版本和异常信号做分层抽样，提高失败、长轨迹、高成本和低置信样本比例，再加一部分随机样本防选择偏差。离线用确定性验收器、标注 rubric和多评审一致性；LLM-as-judge只做经人工校准的一个信号，盲化模型来源并定期复核偏差。线上可看任务完成、重试、人工接管、撤销和后续重复提问等隐式信号。抽检结果进入版本化 badcase集和修复优先级。”

### 出现 Badcase 时如何快速定位是哪个环节、哪个 Agent 出的问题？如何判断该对哪个 Agent 做 SFT 优化？

> “依靠 trace把一次任务拆成路由、检索、规划、每个 Agent、模型和工具 span，每个节点保存版本、结构化输入输出、证据、状态和耗时。Badcase先定位最早偏离点：上下文缺失、路由错、工具参数错、工具脏数据、生成未遵证据还是验收漏检，再归属 owner；后续错误可能只是传播结果。只有当某 Agent在稳定输入/工具下反复出现可学习的行为错误，且 prompt/规则/模型不能经济解决、又有足够高质量示范时才做 SFT。数据或协议问题应修系统，不用微调掩盖。”

### Prompt 调优出现「修好一类、坏了另一类」的回归问题怎么解决？

> “把 Prompt当代码：建立覆盖主要意图、边界和历史 badcase的冻结回归集，每次变更只解决一个明确假设，跑全量切片并比较任务成功、安全、成本和延迟。修一类坏一类说明指令冲突或模型容量不足，我会拆路由/阶段提示、用结构化 schema和工具规则替代更多文字，而不是继续堆补丁。新版本 canary并保留旧版快速回滚；对不可同时满足的目标明确优先级。最终把稳定硬约束移到代码校验，减少 prompt回归面。”

### Prompt 调到极限后，优先换模型、调参数还是上 SFT？各自的判断依据是什么？

> “先确认瓶颈：知识缺失用 RAG/工具，格式/约束用 schema和代码，随机性用温度/采样，基础推理能力不足才换更强模型。换模型是最快基线，但要比较成本延迟和兼容；参数调节只能在现有能力附近取舍；SFT适合大量稳定、重复的领域行为且有高质量数据和维护预算。我的顺序通常是修上下文/工具/评测，跑多模型基线，调少量参数，再以单位成功成本决定是否 SFT。任何方案都要在同一回归集和线上灰度验证。”

### 代码单测的分支覆盖率怎么统计、代码插桩（instrumentation）的原理是什么？

> “分支覆盖率统计 if/else、三元、switch case、逻辑短路等每个出口是否执行，和语句/函数/行覆盖不同。插桩工具先把源码解析为 AST，在语句、函数入口和每个分支插入计数器，自测运行时累加到 coverage对象，结束后结合 sourcemap映射回源码并生成报告。V8覆盖可利用引擎收集执行区间，再由工具转换。高覆盖不等于好测试，还要 mutation testing和行为断言，且转译、动态代码与忽略规则会影响口径。”

### Agent 工具调用的成功率如何定义与度量（成功 / 失败 / 超时 / 脏数据口径）？项目中最初的数据是多少、后续通过哪些手段提升？

> “我分四层口径：模型是否选对工具；参数 schema/业务校验是否通过；传输执行是否在 deadline内成功；结果是否完整、干净并被任务正确使用。超时、429、5xx、权限拒绝、业务空结果和脏数据分别统计，不能都算‘失败’，重试后成功也记录首试和最终成功率。分母按 eligible calls或任务定义并版本化。提升手段包括工具描述去重、严格 schema、候选过滤、参数补全前置查询、超时/幂等重试、结果断言和 fallback。初始与提升数字只报真实 dashboard，缺数据就明确测量方案。”

### Prompt 模板如何管理、测试和灰度发布（作为版本化制品，如何验证改动效果、平滑上线、出问题时回滚）？

> Prompt 应作为带版本号、适用模型、变量 schema、作者、变更说明和评测结果的制品管理，禁止直接在线覆盖。提交时先做变量与结构校验，再跑固定回归集、对抗集和成本/延迟基准；评分同时看任务成功率、格式遵循、安全和 token 消耗。通过后按用户或请求哈希小流量灰度，记录 promptVersion 到每条 trace，比较新旧版本指标并设置自动停止阈值。版本不可变，发布只切换别名；异常时一键把别名指回上一稳定版本，并保留完整审计记录。

## Agent 产品与业务落地

### 如何设计一个订单客服 Agent；转人工这一块怎么处理；转人工意图自动识别怎么做；Agent 意图识别怎么调优？

> “订单客服先做身份与订单绑定，再按查物流、取消、退款、发票、投诉等意图路由；查信息调用只读权威 API，退款等动作先校验政策、展示影响并让用户确认，服务端幂等执行。知识回答必须引用当前政策。转人工既支持用户明确要求，也由低置信、连续失败、负面情绪、高价值/合规风险和工具故障触发；移交包含对话摘要、订单、已做步骤和证据，让人工不必重问。意图模型用分层标签、规则+分类器/LLM、阈值和澄清，基于混淆矩阵与人工改判持续调优。”

### 如何进行意图识别（Agent 路由 / 分发逻辑，根据用户输入选择对应 Agent 或工具）？

> “路由前先做安全、身份和会话状态检查，再用规则处理显式命令/高风险词，分类器或小模型输出可多标签的意图、实体、置信和候选能力；高置信走对应 Workflow/Agent，低置信在少数候选中用 LLM或向用户澄清，unknown有专门兜底。工具选择还受权限、前置条件、健康度和成本过滤。训练和评测看每意图 precision/recall、混淆和误路由代价，不只看总准确率；线上记录人工修正和后续成功作为反馈。”

### 并行化意图识别是什么、为什么要做、如何实现（与普通串行意图识别的区别、适用场景）？

> “串行识别先做一个分类再执行，延迟低、成本小；并行化是在一次输入可能同时包含多个独立目标，或需要规则、语义分类、检索候选等多个信号时并发运行，再由聚合器去重、排序和构建依赖 DAG。例如‘查物流并修改发票’可并发读信息，但修改要等身份/订单确认。实现上共享 deadline和取消，结果带意图 ID、实体、置信、证据和依赖；设 fan-out/成本上限。简单单意图不应并行，否则只会增加冲突和成本。”

### 场景题：用 Agent 实现广告投放的自我迭代（自动判别哪种广告投放方式最优并执行），你怎么设计？

> “我不会让 Agent无约束地自我修改预算。先把目标定义为在 CPA/ROAS、品牌安全、频控和总预算约束下优化；数据层接曝光、点击、转化并做归因和延迟校正，策略层生成受限候选，实验平台用多臂老虎机或 A/B分配小流量，统计显著后逐级放量。执行工具只允许白名单受众、素材和预算范围，高额变更人工审批。监控数据漂移、作弊、探索损失和因果偏差，异常自动停止/回滚。LLM适合生成假设与素材解释，最优判定依赖统计和业务规则，不由模型自评。”

### 知识库 / RAG 能否解析语音与视频，图片是怎么存储的，Excel 表格是怎么切分的（多模态 / 结构化文档解析）？

> “可以，但要先把模态转成可检索表示并保留原件。语音做 ASR、说话人和时间戳，视频按镜头/时间片抽帧、ASR、OCR和 caption，分别建文本与多模态向量；结果通过时间码回到播放器。图片原件放对象存储，索引只存 URI、hash、权限、bbox/caption/embedding，避免把二进制塞向量库。Excel按 sheet识别标题、合并单元格和表区域，小表整体序列化，大表按逻辑行块切且每块重复列头，同时保留单元格范围和公式。所有解析都做权限、版本和质量置信。”

### 当前 Agent 技术的发展阶段与现状你怎么看，现阶段适合落地在哪些业务场景（客服 / 代码 / 数据分析 / 流程自动化）？

> “我认为 Agent已从 Demo进入‘局部可靠、系统约束下可生产’阶段：模型的工具使用和代码能力明显提升，但长任务稳定性、成本、权限、安全和评测仍是主要瓶颈。最适合的是目标可验证、工具数字化、动作可回滚且有人审通道的场景，如客服辅助、代码修改与测试、数据分析、内部知识和半结构化流程自动化。不适合无监督承担高风险最终决策或模糊成功标准的开放任务。落地策略是确定性 Workflow包住局部自主决策，从只读/copilot开始，用成功率与单位成本逐步扩大权限。”
