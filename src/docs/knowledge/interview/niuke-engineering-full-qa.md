## 性能优化

### NQ-161

<!-- niuke-id:NQ-161 source-line:228 -->

**问题：** 前端性能优化有哪些手段（编译 / 网络 / 渲染性能）？首屏加载速度怎么优化？页面打开很慢可能是哪些问题？路由懒加载为什么能优化首屏、改善 LCP？为什么做预加载和骨架屏、弱网降级？

**面试者标准回答：**

> “我按编译、传输、执行和渲染四层优化：构建时 tree shaking、路由分包和压缩；网络侧 CDN、HTTP 缓存、压缩、连接复用和关键资源优先级；运行时减少长任务、重复计算和内存泄漏；渲染侧控制 DOM、布局抖动和大列表。首屏先用真实数据定位 LCP 元素和阻塞链，再减少首包 JS、懒加载非首屏路由、预加载真正关键资源、优化图片与字体。骨架屏改善感知但不等于指标变快。弱网提供低清资源、缓存和可重试降级。路由懒加载只有把非首屏代码移出入口 chunk 才会改善首屏，若拆得过细造成请求瀑布也可能变慢。”

### NQ-162

<!-- niuke-id:NQ-162 source-line:229 -->

**问题：** 性能优化量化：每个优化方法分别提升了多少、为什么能提升这么多？性能优化案例（首屏加载、资源压缩、CDN 策略）？

**面试者标准回答：**

> “性能收益必须用同一设备、网络、数据集和版本前后对照，报告中给中位数与 P75/P95，而不是凭感觉写‘提升 50%’。例如我会记录首屏 JS 从多少 KB 降到多少、LCP 从多少秒降到多少、长任务总时长和错误率变化，并用构建分析、RUM 和实验组相互印证。资源压缩主要减少传输字节，CDN 缩短 RTT，缓存消除重复传输，代码分割减少初始解析执行；各自作用链路不同。若没有真实数据，我会明确说是预期收益和验证方案，不编造项目数字。”

### NQ-163

<!-- niuke-id:NQ-163 source-line:230 -->

**问题：** 出现白屏问题如何排查？前端性能指标（FCP / LCP / CLS / FPS）怎么采集？LCP 是什么、如何查看？FCP 指什么、如何测量？FP / FCP 区别？

**面试者标准回答：**

> “白屏先区分资源没到、脚本异常、路由/鉴权死循环、接口阻塞、CSS 隐藏、容器兼容和版本缓存，结合 Network、Console、错误平台、发布版本和最小复现定位。FP 是首次像素变化，FCP 是首次渲染文本、图片或非白色 canvas 等内容；LCP 是视口内最大候选内容元素的渲染时间，常代表主内容出现。用 DevTools Performance/Lighthouse 本地分析，用 PerformanceObserver 或 web-vitals 做真实用户采集。CLS 衡量非预期布局移动，FPS 只能辅助观察流畅度。LCP 候选会随页面加载更新，不是发现第一个大元素后就永远固定。”

### NQ-164

<!-- niuke-id:NQ-164 source-line:231 -->

**问题：** 懒加载策略：IntersectionObserver API 和 loading="lazy" 的区别？图片懒加载原理与手写核心逻辑（offsetTop）？表格懒加载（分页 / 按需请求）具体怎么实现（触发条件、前后端配合）？

**面试者标准回答：**

> “`loading=lazy` 是浏览器对图片/iframe 的原生启发式加载，成本低但控制有限；IntersectionObserver 能观察任意目标与根视口交叉，适合组件、埋点和自定义阈值。旧式 offsetTop 方案要在滚动时节流，比较元素位置与 scrollTop+viewportHeight，但会触发布局读取，优先不用。表格懒加载以分页游标和稳定排序为契约，底部哨兵触发下一页；前端用 loading/hasMore/requestId 防重复和乱序，后端返回 nextCursor、数据与是否结束。图片必须预留宽高，避免懒加载造成 CLS。”

### NQ-165

<!-- niuke-id:NQ-165 source-line:232 -->

**问题：** 极大量数据（如 10 万条）下拉加载仍卡顿如何进一步优化？虚拟列表 / 虚拟滚动的实现思路（原理、实现方式、前缀高度表 + 二分查找、合并单元格时懒加载数据结构与渲染逻辑）？瀑布流怎么做、用过虚拟列表吗？

**面试者标准回答：**

> “下拉加载只解决网络分批，不解决 DOM 持续增长。虚拟列表只渲染可见窗口加 overscan，固定高度用下标乘行高；动态高度维护测量缓存和前缀高度表，通过二分从 scrollTop 找起点，测量变化后更新后续偏移。合并单元格要把逻辑分组、跨页 span 和占位关系作为数据模型，不能只看当前页。瀑布流可用 CSS columns/masonry 或按列累计高度分配，虚拟化时还需空间索引。若交互只需近期数据，也可上限淘汰旧 DOM、分页和服务端筛选。”

### NQ-166

<!-- niuke-id:NQ-166 source-line:233 -->

**问题：** 频繁 append + 一次性渲染几十万行节点导致主线程阻塞、页面卡顿怎么优化（分片渲染 requestIdleCallback / DocumentFragment）？滚动触底加载导致 DOM 过多卡顿如何优化（除虚拟列表外）？长列表遍历阻塞主线程如何解决（Web Worker）？

**面试者标准回答：**

> “DocumentFragment 只减少多次插入的中间更新，一次创建几十万节点仍会阻塞。我会先虚拟化；无法虚拟化时用 requestAnimationFrame/requestIdleCallback 分片并设置每批时间预算，配合骨架、取消和进度。滚动列表还可分页、折叠、限制历史窗口、Canvas 绘制或服务端聚合。纯数据计算转 Web Worker，使用 Transferable 降低拷贝成本，但 DOM 只能在主线程更新。关键是控制单个长任务小于约 50ms，并用 Performance 面板验证。”

### NQ-167

<!-- niuke-id:NQ-167 source-line:234 -->

**问题：** ECharts 中 canvas 和 SVG 区别、优缺点？ECharts 图表自适应、放大缩小卡顿 / 动画卡顿怎么处理？复杂计算阻塞主线程怎么办？多图表向下滚动白屏卡顿怎么优化？如何监控每个组件的性能数据？D3 与 ECharts 的区别？为什么选偏底层的 D3？点击热力图、请求数量限制？

**面试者标准回答：**

> “Canvas 是位图绘制，图元多时通常更合适但单元素交互和可访问性较弱；SVG 保留 DOM 图元，少量元素、清晰缩放和定制交互更方便，数量大时 DOM 成本高。ECharts 卡顿我会关掉非必要动画和 symbol、采样/聚合数据、增量更新而非重建实例、ResizeObserver 防抖，并只在图表进入视口时初始化，离开后暂停或 dispose。复杂聚合放 Worker。ECharts 偏配置化图表，D3 偏数据绑定与可视化原语，极强定制才选 D3。热力图点击请求要取消旧请求、限并发、缓存和只消费最新结果。组件性能用 User Timing、PerformanceObserver 与统一埋点关联组件名和版本。”

### NQ-168

<!-- niuke-id:NQ-168 source-line:235 -->

**问题：** 用户反馈页面加载慢 / 白屏怎么定位？项目发布到线上后如何监控整体服务质量（埋点 SDK、性能指标 SDK 内部实现、告警推送）？服务端优化方案（CDN vs COS 存储优势）？

**面试者标准回答：**

> “线上定位必须把用户环境和请求链串起来：埋点 SDK 采集导航与 Web Vitals、资源失败、JS 异常、接口耗时、长任务和版本号，抽样后批量上报；用 session/user/request/trace ID 关联日志，并按 P75、错误率和影响用户数告警。告警要去重、抑制风暴、分级路由并附发布变更。服务端从 DNS、CDN、网关、源站和数据库逐段看耗时。COS/对象存储负责低成本高持久保存源文件，CDN 负责边缘缓存和分发，通常组合使用。”

### NQ-169

<!-- niuke-id:NQ-169 source-line:236 -->

**问题：** 用户操作卡顿如何快速定位问题？了解控制台的 Performance 面板吗、具体怎么用它分析长任务与火焰图？

**面试者标准回答：**

> “我先记录一次可复现操作的 Performance trace，开启 CPU/网络降速以放大问题。看 Main 线程中超过 50ms 的 Long Task、红色三角告警、底部摘要的 scripting/rendering/painting，再从火焰图向下找到耗时调用栈；同时检查 Layout、Paint、内存增长和帧轨道掉帧。React/Vue Profiler 用于组件级重复渲染，Network 用于请求等待。定位后做单变量修改并重新录制，而不是看到某个函数在火焰图上就直接下结论，因为它也可能只是调用链入口。”

### NQ-170

<!-- niuke-id:NQ-170 source-line:237 -->

**问题：** prefetch 和 preload 分别是什么作用、有什么区别（优先级 / 加载时机 / 使用场景）？怎么验证 prefetch 到底有没有生效？LCP 的测量终点是固定的吗？

**面试者标准回答：**

> “preload 声明当前导航很快需要的关键资源，优先级通常较高，必须给正确 `as` 和 crossorigin，否则可能重复下载；prefetch 提示浏览器在空闲时准备未来导航资源，优先级低且浏览器可忽略。验证要看 Network 的 Initiator、Priority、Timing 与后续是否来自缓存，也可查 PerformanceResourceTiming，不能只看标签存在。LCP 在加载期间会更新候选；通常在页面隐藏或首次用户输入等终止条件后确定最终值，因此测量终点不是固定毫秒数。”

## 构建与部署

### NQ-171

<!-- niuke-id:NQ-171 source-line:241 -->

**问题：** Vite 为什么启动很快？Vite 热更新原理？为什么选 Vite？Vite 如何兼容老浏览器？Webpack 与 Vite 的区别（含 Rollup / RSpack 迁移兼容性）？

**面试者标准回答：**

> “Vite 开发时不先把应用整体打包，而是利用浏览器原生 ESM 按需转换源码；依赖会预构建以兼容 CommonJS并减少请求数，所以冷启动快。文件变更后服务端通过 WebSocket 发送 HMR 更新，模块沿接受边界重新执行，框架插件尽量保留组件状态。生产构建仍做打包优化。老浏览器可用官方 legacy 插件生成兼容产物和 polyfill，但要先定义 browserslist。Webpack 是高度可配置的 bundle-first 工具；Vite 更偏 ESM 开发服务器加生产构建工具。Rollup常用于库和 Vite 生产链路，Rspack追求 Webpack API/生态兼容与更快实现；迁移要实测插件、loader、产物和 SSR，而非只比较速度。”

### NQ-172

<!-- niuke-id:NQ-172 source-line:242 -->

**问题：** Webpack 打包流程？loader 和 plugin 的作用？Webpack 对动态 import() 怎么拆 chunk、运行时怎么加载？哪些情况没把模块拆成独立 chunk？splitChunk 怎么配置？webpack 热更新原理？Tree-Shaking 原理、打包工具如何实现？

**面试者标准回答：**

> “Webpack 从入口解析模块，loader 把非 JS 或新语法转成可处理模块，构建依赖图、优化 chunk，最后由 plugin 在各生命周期钩子参与提取 CSS、生成 HTML等并输出资源。动态 `import()` 通常形成异步 chunk，运行时创建 script 加载并注册模块；若模块已在同步图、被 splitChunks 合并、内联或受配置限制，就不一定独立成块。splitChunks 按 chunks、minSize、minChunks、cacheGroups 等控制公共依赖。HMR 通过更新清单与 chunk 通知客户端，只替换可接受模块，否则刷新。Tree shaking依赖 ESM 静态导入导出、sideEffects 标记和压缩器删除不可达代码，动态访问和副作用会限制效果。”

### NQ-173

<!-- niuke-id:NQ-173 source-line:243 -->

**问题：** 分包 / 代码分割 / 路由懒加载（React.lazy + Suspense）？代码分割是否越细越好、判断标准？小程序分包思想怎么落地？分包策略（按路由分块 + 公共依赖提取，preload 优化 LCP）？模块联邦？

**面试者标准回答：**

> “代码分割目标是让关键路径更短，不是 chunk 越多越好。常见策略是路由级懒加载，稳定大依赖按复用与缓存边界抽公共包，首屏关键子组件可预加载；React 用 `lazy(() => import())` 配合 Suspense。判断看初始字节、请求瀑布、解析执行时间、缓存命中和重复模块。小程序分包把启动必需放主包、业务页放分包并按平台规则预下载。模块联邦适合独立团队运行时共享/加载模块，但带来版本协商、故障隔离、类型和治理成本，不应只为分包使用。”

### NQ-174

<!-- niuke-id:NQ-174 source-line:244 -->

**问题：** 路由懒加载 + 页面过渡动画实现思路？加载延迟怎么处理？React 组件懒加载失败如何捕获与处理（Error Boundary）？

**面试者标准回答：**

> “路由切换时先启动数据和代码请求，旧页是否保留到新页就绪要按产品体验决定；过渡动画作用于稳定容器，避免异步组件装载导致闪烁。Vue 可用动态 import 加 RouterView/Transition，React 用 lazy/Suspense。加载超过短阈值再显示骨架，避免瞬时闪屏。懒加载失败要由 Error Boundary 捕获，识别网络故障和发布后 chunk 失效，提供有限重试或刷新到新 HTML；重试 import 要改变请求或重新加载文档，且必须防止无限刷新循环。”

### NQ-175

<!-- niuke-id:NQ-175 source-line:245 -->

**问题：** i18n 国际化方案（i18next + react-i18next）？语言包很大怎么优化（动态 import）？

**面试者标准回答：**

> “我把翻译按语言和 namespace/路由拆包，启动只加载当前语言的公共词条，进入页面再动态 import 对应 namespace，切换语言时缓存已加载资源并设置 fallback。i18next 负责 key、插值、复数和回退，react-i18next 用 provider/hook 触发局部更新。翻译内容默认按文本处理，富文本使用受控组件占位，不直接插入 HTML。还要处理日期、数字、货币、时区、RTL、缺失 key 监控和服务端渲染时客户端语言一致，避免 hydration 不匹配。”

### NQ-176

<!-- niuke-id:NQ-176 source-line:246 -->

**问题：** Nginx 部署与 HTTPS 证书配置？部署方式有哪些？测试和生产环境打包有什么侧重点？SSR / ISR / 离线包？SSR 的作用、nextjs 的水合问题？BFF 上游服务报错机制？

**面试者标准回答：**

> “静态 SPA 可由 Nginx 提供带 hash 资源长缓存、HTML 短缓存，并配置 history fallback；TLS 要完整证书链、自动续期、现代协议和 HTTP 到 HTTPS 跳转。部署可选静态托管/CDN、容器、SSR 服务或离线包，测试环境重 sourcemap和诊断，生产重压缩、安全、可观测与回滚。SSR改善首屏内容与 SEO，但增加服务成本；ISR在构建后按规则增量生成，离线包适合 App 容器。Next 水合要求服务端与首次客户端渲染一致。BFF 聚合上游时要设超时、错误映射、追踪和局部降级，不能把所有上游错误都变成 500。”

### NQ-180

<!-- niuke-id:NQ-180 source-line:250 -->

**问题：** 项目里 Next.js 是用来做什么的？它算是这个项目的后端吗（SSR / API Routes / 全栈边界怎么划分）？

**面试者标准回答：**

> “Next.js 在项目中可能承担文件路由、服务端渲染/静态生成、Server Components、数据获取和 API Route/Route Handler。它可以运行服务端代码，所以具备 BFF或轻量全栈能力，但不自动等于整个业务后端。认证聚合、页面专属接口可放 Next；复杂领域规则、长任务、独立扩缩容和多端共享服务通常放专门后端。边界依据团队能力、部署拓扑、数据所有权和故障隔离划分，而不是因为文件能写在同一仓库就全部塞进去。”

### NQ-181

<!-- niuke-id:NQ-181 source-line:251 -->

**问题：** Next.js 的客户端组件（Client Components）与服务端组件（Server Components）的区别是什么、各自适用什么场景（'use client' 边界、数据获取与打包体积）？

## 安全与登录

### NQ-191

<!-- niuke-id:NQ-191 source-line:267 -->

**问题：** 双 Token（AccessToken + RefreshToken）无感登录怎么实现？RefreshToken 也过期了怎么处理？基于双 token 实现单点登录？并发请求、登录态管理、持久化、鉴权？

**面试者标准回答：**

> “Access Token短效用于访问资源，Refresh Token长效且只用于换新；Web端优先把 refresh放 Secure、HttpOnly、SameSite Cookie，access尽量放内存。遇401时只允许一个刷新请求，其余请求排队，刷新成功后重放一次；刷新失败清理状态并跳登录，不能循环。Refresh也过期或被撤销时必须重新认证。安全实现还要做 refresh轮换、复用检测、设备/会话记录、撤销和 CSRF防护。SSO通常由统一身份提供方走授权码加 PKCE建立各应用自己的会话，双 token只是令牌生命周期机制，不等于 SSO本身。”

### NQ-192

<!-- niuke-id:NQ-192 source-line:268 -->

**问题：** 鉴权放在哪一层（网关 / 登录中台 / 业务服务）？按钮级别前端权限如何实现、页面刷新时如何恢复路由与权限信息、只靠前端是否足够（后端如何兜底）？RBAC 权限系统设计？

**面试者标准回答：**

> “鉴权分层：身份中台负责登录和令牌，网关做通用签名、过期、限流和粗粒度策略，业务服务依据资源和领域规则做最终授权。前端权限只用于菜单、路由和按钮体验，不能作为安全边界。RBAC至少有用户、角色、权限、用户角色、角色权限，复杂场景再叠加租户、资源范围或 ABAC条件。刷新时先恢复安全会话，再拉取权限快照并动态生成路由；加载期间显示明确状态。任何接口都由后端校验，按钮隐藏也要考虑深链、旧缓存和权限变更。”

### NQ-193

<!-- niuke-id:NQ-193 source-line:269 -->

**问题：** XSS / CSRF 前端防御（见网络章节）。

**面试者标准回答：**

> “XSS防御以按上下文输出编码为核心，避免危险 DOM API，富文本用白名单净化，并以 CSP、Trusted Types和 HttpOnly Cookie降低影响；React/Vue文本插值默认转义，但原始 HTML入口仍危险。CSRF利用浏览器自动携带登录凭证，防御用 SameSite Cookie、CSRF Token、Origin/Referer校验和敏感操作确认。两者不能混为一谈：XSS是在目标源执行脚本，CSRF通常无法读取响应，只能借身份发请求；若存在 XSS，多数 CSRF防线也可能被绕过。”

## Git 与质量

### NQ-194

<!-- niuke-id:NQ-194 source-line:273 -->

**问题：** Git 协作：Merge 和 Rebase 的区别与使用场景？冲突解决？本地 commit 5 次未 push，回滚到第 3 次后如何找回第 4、5 次（stash / cherry-pick / amend / force push）？常用 git 命令？

**面试者标准回答：**

> “Merge保留分支拓扑并创建合并提交，适合共享分支；Rebase把提交重放到新基线，历史线性但会改 commit hash，只用于尚未共享或团队明确约定的分支。冲突时理解两边意图、修改文件、运行测试后 add并 continue。误把本地5次提交回到第3次，先用 `git reflog`找到第4、5次，再建安全分支或 cherry-pick恢复；stash用于未提交改动，amend改最近提交。已推送共享历史尽量 revert，不随意 force；必要时用 `--force-with-lease`并协调团队。”

**问题：** 如何保证代码质量 / 不引发线上问题（除 eslint 外、除 AI 工具外）？渐进式迁移？项目开发前有没有提前思考性能问题？

**问题：** AI 辅助与工程质量：平时如何借助 AI 工具提高效率、解决问题？如何判断和验收 AI 生成的代码是否可用、可维护、符合项目规范？用 AI 改代码时是否用单元测试 / 集成测试避免新 bug？AI 生成代码占比、如何把控质量？vibe coding / Spec Coding 流程、中途错了怎么改正？用 AI 工具辅助工程化（如 Harness / Spectacle）？

## 文件与上传

### NQ-198

<!-- niuke-id:NQ-198 source-line:280 -->

**问题：** 大文件分片上传的哈希计算怎么做（md5）？断点续传怎么知道哪些分片已经传过？大文件上传弱网怎么办？

**面试者标准回答：**

> “浏览器用 File.slice分片，hash计算放 Worker并增量读取，避免一次把大文件载入内存；MD5适合内容标识但不具备抗碰撞安全性，完整性要求更高可用 SHA-256。先初始化上传拿 uploadId，服务端返回已存在分片索引与校验值，客户端只补缺片；每片以 uploadId+index幂等，完成后服务端校验整文件再合并。弱网降低并发、设置超时和带抖动重试、持久化会话并支持暂停恢复；秒传必须由服务端基于可信记录确认，不能只相信客户端 hash。”

### NQ-199

<!-- niuke-id:NQ-199 source-line:281 -->

**问题：** 文件下载断点续传（基于 HTTP Range）怎么实现？文件上传如何显示上传进度？

**面试者标准回答：**

> “下载续传时客户端发送 `Range: bytes=start-`，服务端支持则返回206、Content-Range和剩余字节；还要用 ETag/If-Range确认文件版本未变，若返回200就应从头处理。浏览器普通下载的断点能力受 API和存储限制，桌面端可写入临时文件。上传进度可由 XHR upload progress得到已发送字节，但它不等于服务端持久化完成；分片上传应以已确认分片字节加在途分片进度汇总，重试时防止重复累计，并显示服务端合并阶段。”

## 后端 / 数据 / 高并发（前端视角）

### NQ-200

<!-- niuke-id:NQ-200 source-line:285 -->

**问题：** 为什么后端用 mongoDB 而不用 mysql（对比）？对 redis 的理解？本地数据库用的什么？IndexDB 与 Dexie 对比？

**面试者标准回答：**

> “MongoDB文档模型适合字段变化快、聚合边界清晰和嵌套读取多的场景，MySQL关系模型适合强约束、复杂关联和成熟事务；选型看访问模式、一致性与团队能力，不用‘NoSQL更快’概括。Redis是内存数据结构服务，常用于缓存、限流、会话、队列辅助和分布式协调，需处理淘汰、持久化、缓存穿透/击穿和一致性。浏览器本地结构化数据用 IndexedDB；Dexie是其 Promise化封装，提供 schema、事务和查询便利，但仍受浏览器配额与同源限制。”

### NQ-201

<!-- niuke-id:NQ-201 source-line:286 -->

**问题：** 高并发场景：1s 内对数据库 10w 次写入如何优化？后端高并发 1w 个接口都 down 了怎么处理？

**面试者标准回答：**

> “10万写/秒要先聚合和削峰：入口限流与批量 API，消息队列持久化，消费者批写，数据库分区/分片、合适索引和幂等键，并用背压保护下游；是否允许最终一致决定架构。若上万接口或实例集中故障，先熔断、降级非核心功能、扩容和流量切换，阻止无限重试风暴，再根据指标定位网关、连接池、数据库或依赖瓶颈。前端只做有限重试、明确状态和任务查询，不能把后端容量问题用防抖掩盖。”

### NQ-202

<!-- niuke-id:NQ-202 source-line:287 -->

**问题：** 消息队列相关：RabbitMQ / Celery 解耦异步任务（投递链路、交换机、持久化、死信 / 延迟队列、优先级、重试）；高并发下为何弃 Redis List/Stream 选 RabbitMQ；消息丢失 / 重复消费 / 死信堆积前后端如何兜底？多消息投递结果如何与发送请求对应？

**面试者标准回答：**

> “典型链路是生产者发布到 RabbitMQ exchange，经 routing key到持久化 queue，开启 publisher confirm、持久消息和消费者手动 ack；失败按次数与错误类型重试，延迟可用 TTL+死信或延迟插件，最终进入 DLQ并告警。Celery负责分布式任务执行。相比 Redis List/Stream，RabbitMQ在路由、确认、死信、优先级和成熟运维上更完整，但选择仍看吞吐与团队。端到端采用 at-least-once更常见，所以消费者用业务幂等键；消息带 correlationId/requestId，前端拿 taskId查询或订阅状态。死信堆积要暂停扩散、分类修复和可审计重放。”

### NQ-203

<!-- niuke-id:NQ-203 source-line:288 -->

**问题：** 异地数据同步如何实现？多用户并发操作同一资源竞态冲突（前端锁 / 服务锁 / 分布式锁）？

**面试者标准回答：**

> “异地同步先定义 RPO/RTO和冲突模型，可用数据库日志 CDC经消息系统复制，带全局 ID、版本、顺序和幂等消费；双写要避免把网络调用塞进本地事务，可用 outbox和最终对账。多用户修改同一资源优先乐观锁：提交版本号或 ETag，条件更新失败后提示合并；必须串行的短临界区才用数据库/服务锁。分布式锁要有租约、续期、唯一持有者和 fencing token，防止过期持有者继续写。前端锁只防本页面重复点击，不能解决跨用户竞态。”

### NQ-204

<!-- niuke-id:NQ-204 source-line:289 -->

**问题：** 如何上报埋点的 api、如何确保页面关闭前请求正确发送（beforeunload）？告警推送实现方法？

**面试者标准回答：**

> “埋点 SDK把事件写入内存队列，补充时间、页面、会话、版本和采样字段，按数量/时间批量 POST；卸载时用 `navigator.sendBeacon`，或 `fetch(..., {keepalive:true})`发送小请求，不能依赖异步 beforeunload完成，也应监听页面 visibilitychange。服务端校验 schema、去重和限流。告警由指标/日志系统按窗口和阈值聚合，关联版本与影响用户，去重、静默和升级后推送到值班渠道；重要的是可行动信息和恢复通知，而不是每个错误发一条消息。”

### NQ-205

<!-- niuke-id:NQ-205 source-line:290 -->

**问题：** 如果由你设计后端，数据库表结构怎么设计、表与表之间关系（一对一 / 一对多 / 多对多）如何处理？

**面试者标准回答：**

> “我先从业务用例、实体生命周期和查询模式建模，再确定主键、唯一约束、状态、审计字段、索引和数据保留。1:1可把强同生命周期字段同表，或用带唯一外键的扩展表；1:N在多的一方放外键；N:M用关联表，联合唯一键防重复，并可存关系属性。外键是否物理约束取决于规模和治理，但逻辑一致性必须有。还要设计软删除、租户键、乐观锁版本、事务边界和迁移，不会只画表关系而忽略访问路径与索引成本。”

### NQ-206

**问题：** 有 Node.js 服务端开发经验吗？用过 Egg.js 之类的 Node 企业级框架吗、约定式目录与插件机制是怎样的？

**面试者标准回答：**

> “我有 Node服务端经验时会重点讲事件循环、异步 I/O、错误边界、流与背压、进程模型、鉴权和可观测，而不只说会写接口。Egg.js一类企业框架通过约定目录组织 controller、service、middleware、config和插件，IoC/加载器按约定装配上下文；插件声明依赖并扩展框架能力。优势是团队一致、生命周期和生态，代价是框架约定与升级成本。无论框架都应保持 controller薄、领域逻辑可测试、输入校验、超时取消、结构化日志和优雅退出。”
