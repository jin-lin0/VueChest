# Agent 核心标准问答

本文面向 Agent / AI 应用开发岗位。答案重点放在系统边界、工程取舍和可验证性，不把“会调用模型 API”包装成 Agent 经验。

---

## 一、Agent 架构与推理

### Q1：什么是 Agent？它和普通 LLM 调用、Workflow 有什么区别？

> “普通 LLM 调用主要是输入到输出的一次映射；Workflow 由代码预先规定执行路径；Agent 则让模型在目标和约束下，动态决定下一步、选择工具、观察结果并继续调整。工程上我通常把 Agent 拆成模型、上下文、状态、工具执行器、循环控制和评测观测几个部分。
>
> 三者不是能力等级越高越好。固定流程能解决的问题，我优先 Workflow，因为它更便宜、可预测、容易测试；只有步骤无法穷举、需要根据中间结果动态行动，并且错误成本可控时，我才引入 Agent。很多生产系统其实是确定性工作流包住少量 Agent 节点。”

**追问：Agent 的核心是 ReAct 吗？**

> “ReAct 是常见循环范式，不是 Agent 的唯一标准。核心是模型拥有受约束的决策权，并能基于环境反馈调整行动。具体实现可以是 ReAct、规划执行、状态图或自定义控制器。”

### Q2：什么场景不应该使用 Agent？

> “我会看任务是否真的需要动态决策。固定审批流、强一致交易、简单分类抽取、严格低延迟接口，通常不应该让 Agent 自由规划。高风险动作如果缺少权限隔离、审计和人工确认，也不适合直接 Agent 化。
>
> 我会先用单次调用、检索加生成或确定性工作流建立基线；只有基线在复杂分支和未知步骤上明显不足，而且 Agent 的质量收益能覆盖额外延迟、成本和失败面时才升级。”

### Q3：Agent Loop 怎么设计？如何避免死循环和预算失控？

> “一个典型循环是读取目标与状态、模型决策、校验动作、执行工具、记录 observation、更新状态，再判断完成或继续。循环控制必须在模型外由确定性代码掌握，不能只相信模型输出‘完成了’。
>
> 我会设置最大步数、总 token、总耗时、单工具超时和费用预算；检测相同工具加相同参数的重复调用、连续无状态进展和不可恢复错误。结束条件既包括成功验收，也包括预算耗尽、用户取消、需要补充信息和高风险操作等待确认。关键状态要持久化，便于中断恢复，而不是从头重跑。”

```ts
while (!state.done && state.steps < limits.maxSteps) {
  assertWithinBudget(state, limits)
  const decision = await decide(state)
  const action = validateDecision(decision)

  if (requiresApproval(action)) {
    await checkpoint(state, { status: 'waiting_approval', action })
    break
  }

  const result = await executeWithTimeout(action)
  state = reduceState(state, action, result)
}
```

### Q4：ReAct、Plan-and-Execute、Reflection 怎么选？

> “ReAct 把推理、行动和观察交替进行，适合需要边查边调整的任务；Plan-and-Execute 先形成高层计划，再逐步执行，适合步骤较多且可以分解的任务，但计划必须允许局部重规划；Reflection 在执行结果后增加批评和修正，适合存在可验证反馈的任务。
>
> 我不会默认把三者全叠上。短任务用一次工具调用或简单 ReAct；长任务用计划加状态图；只有错误代价值得额外模型调用，并且 Critic 有可靠证据时才加 Reflection。否则自我反思可能只是让模型更自信地重复错误。”

### Q5：如何判断 Agent 真的完成任务，而不是只生成了漂亮答案？

> “完成条件要落在环境状态或可验证产物上，而不是模型自报。比如订票任务要验证订单 ID 和状态，代码任务要运行测试和静态检查，数据分析要校验查询结果与输出 schema。
>
> 我会把验收器尽量写成确定性规则；难以规则化的语义质量才交给模型评审，并配人工抽检和参考样例。结束时保存行动轨迹、工具结果与验收证据，方便审计和复现。”

## 二、Tool Calling、结构化输出与 MCP

### Q6：Function Calling 的完整链路是什么？模型会真的执行函数吗？

> “应用把工具名称、描述和参数 schema 提供给模型；模型返回要调用的工具和参数；宿主代码解析并校验参数，做鉴权和风险判断，再真正执行函数；最后把带 call ID 的工具结果回填给模型，让它决定继续调用还是生成答案。模型只是在提出结构化调用意图，真正执行、权限和副作用都由宿主负责。
>
> 生产实现还要覆盖 schema 校验失败、工具不存在、超时、重试、并行调用、结果过大和用户取消。工具结果也是不可信输入，不能因为来自内部 API 就直接当高优先级指令。”

### Q7：怎样设计一个模型容易正确调用的工具？

> “工具要单一职责、命名清晰、描述包含使用时机和禁止场景；参数尽量少，用 enum、格式和范围减少歧义，避免让模型拼 SQL 或自由填写内部字段。返回结果保持紧凑、稳定，并区分业务错误和系统错误。
>
> 对写操作我会提供幂等键、dry-run 或 preview，把‘查询’和‘提交’拆开。工具多时先按意图或命名空间检索候选工具，只把相关子集放入上下文；工具描述版本化，并用历史调用样本做选择准确率回归。”

### Q8：JSON Mode、JSON Schema 和 Structured Outputs 有什么区别？

> “JSON Mode 一般只承诺生成合法 JSON，不保证字段符合业务契约；JSON Schema 是字段、类型、枚举和必填项的结构定义；Structured Outputs 是服务商在生成阶段约束输出符合给定 schema 的能力。
>
> 即使使用结构化输出，服务端校验仍不能省，因为还存在语义错误、业务约束、模型拒绝、截断和提供商差异。我的处理链是生成约束、schema 校验、业务校验、有限次修复或重试，最后进入降级或人工处理。”

### Q9：Function Calling 和 MCP 有什么区别？

> “Function Calling 是模型与宿主之间表达‘调用哪个函数、参数是什么’的一类能力；MCP 是 AI 应用连接外部能力的开放协议，规定发现、协商和调用工具或读取资源等交互。它们不在同一抽象层：MCP 服务器可以暴露工具，宿主再把这些工具适配给模型的 Function Calling；也可以接不同模型厂商。
>
> MCP 解决复用和互操作，不会自动解决工具选择正确性、权限、幂等和提示注入。接入外部 MCP Server 时，我仍会做信任分级、能力白名单、凭据隔离、用户同意和结果清洗。”

### Q10：请解释 MCP 的 Host、Client、Server 和三类核心原语。

> “Host 是面向用户的 AI 应用和总协调者，管理权限、上下文和一个或多个 Client；Host 通常为每个 Server 创建独立 Client，Client 负责与对应 Server 交互；Server 暴露某个领域的能力。
>
> 常见原语是 Prompts、Resources、Tools：Prompt 是可复用交互模板，Resource 是可读取的上下文数据，Tool 是可执行动作。按当前 2026-07-28 规范，核心协议是无状态的：请求在 `_meta` 中携带协议版本和客户端能力，Client 可用 `server/discover` 获取 Server 的版本、身份与 capabilities；这和旧版初始化会话不同。规范变化较快，所以项目里必须钉版本并做兼容测试。”

### Q11：工具调用如何做安全和幂等？

> “我会把工具按只读、可逆写、不可逆或高风险分级。所有调用先做 schema 校验和基于当前用户的授权，凭据不进入模型上下文；高风险动作采用查询—预览—用户确认—提交两阶段，并记录审计日志。
>
> 重试只针对明确的瞬时故障，并使用指数退避和抖动。写操作必须有业务幂等键或去重表，不能因为 HTTP 超时就盲目再次扣款。工具输出要限长和转义，来自网页、邮件或文档的内容视为数据，不能覆盖系统策略。”

## 三、RAG 与检索

### Q12：RAG 的完整流程是什么？它解决什么问题？

> “RAG 把模型参数中的知识和可更新的外部知识结合起来。离线侧包括数据解析、清洗、分块、元数据、embedding 和索引；在线侧包括查询理解、改写、过滤、召回、融合、重排、上下文组装、生成和引用。最后还需要评测、反馈和索引更新闭环。
>
> 它适合私有知识、频繁更新和需要证据的问答，但不能自动消除幻觉。召回不到、召回错、上下文冲突或生成没有忠于证据，都会失败。所以我会先判断问题是否需要检索，对无证据场景拒答或澄清，并让答案引用到具体文档片段。”

### Q13：Chunk Size 和 Overlap 怎么选？

> “没有通用最佳数字。块太小，上下文割裂；块太大，主题混杂、召回噪声和 token 成本上升。我的起点是尊重文档结构，按标题、段落、表格或代码单元切分，再给必要的父级标题和来源元数据。Overlap 只用于缓解边界断裂，不能替代语义切分。
>
> 我会从真实问题反推：答案证据通常跨多大范围、检索模型支持多长输入、最终上下文预算多少。用不同切分参数构建索引，在标注问题集上比较 Recall@k、MRR 或 nDCG，再结合答案 faithfulness、延迟和成本选型。”

### Q14：稀疏检索、向量检索、混合检索和 Rerank 有什么区别？

> “BM25 等稀疏检索擅长关键词、编号、专有名词和精确匹配；向量检索擅长语义近似，但可能漏掉罕见词和精确标识。混合检索让两路分别召回，再用 RRF 等方法融合排名，覆盖面更稳。
>
> Reranker 在较小候选集上做更精细的 query-document 相关性判断，通常比 embedding 相似度更准，但增加延迟和计算成本。线上我会让粗召回保 recall，重排保 precision，并根据查询类型、租户和时延预算动态决定候选数。”

### Q15：如何评估一个 RAG 系统？

> “我会分层评估。数据层检查解析和切分完整性；检索层用带证据标注的问题集计算 Recall@k、MRR、nDCG，并切片看不同文档和查询类型；生成层看 answer correctness、faithfulness、引用准确性、拒答质量；系统层再看端到端成功率、P95 延迟、成本和用户反馈。
>
> LLM-as-Judge 可以扩大语义评测规模，但要先用人工样本校准 rubric，避免位置偏差、偏好冗长和自家模型偏差。每次模型、Prompt、索引或切分变更都跑固定回归集，再把线上失败样本脱敏后回流。”

### Q16：RAG 返回错误答案时怎么定位？

> “我先看证据是否存在于知识库：不存在是数据覆盖问题；存在但没切好是解析或 chunk 问题；切片正确但没召回是 query、embedding、过滤或索引问题；召回了但没排前是融合或 rerank 问题；正确证据已进入上下文却答错，才重点看 Prompt、上下文冲突和模型生成。
>
> 因此 Trace 要保留规范化查询、各路候选、分数、过滤条件、重排结果、最终上下文、模型版本和引用。没有这条链路，只看最终回答很难定位。”

### Q17：知识库如何不停服更新？

> “我会把文档版本和索引版本分开管理。新内容先在影子索引完成解析、embedding 和质量校验，增量变更通过队列处理；验证通过后原子切换 alias 或版本指针，旧索引保留一段时间用于快速回滚。删除要传播 tombstone，防止旧片段继续被召回。
>
> 查询链路记录命中的索引版本，便于复现。大规模重建时做双读抽样或离线回放，确认召回指标、延迟和成本，再逐步放量。这样比边写边改唯一生产索引更可控。”

## 四、上下文与记忆

### Q18：上下文窗口和 Memory 是一回事吗？

> “不是。上下文窗口是模型本次推理可见的 token 容量；Memory 是应用选择保存、更新和召回信息的机制。聊天记录塞进上下文只是最简单的短期记忆，并不等于模型永久记住。
>
> 我通常把状态分为当前任务状态、短期对话摘要、长期用户偏好和外部事实知识。每类数据有不同生命周期、可信度和权限，不能都扔进一个向量库。写入长期记忆前要判断是否稳定、是否值得复用、是否经用户允许；读取时也要带来源和时间。”

### Q19：上下文太长怎么办？

> “我不会只依赖截断。先给内容分层：系统约束和当前目标保留，工具描述按需检索，历史对话滚动摘要，事实从外部存储按需召回，大型工具结果压缩成结构化观察。状态与消息分离，避免每轮重放所有中间文本。
>
> 摘要可能丢细节，所以关键 ID、用户确认、约束和未完成事项要结构化存储，不只放自然语言摘要。还要监控输入 token、缓存命中、被裁剪内容和任务成功率；长上下文本身不保证模型能同等利用每个位置的信息。”

### Q20：长期记忆如何避免污染和隐私问题？

> “写入前做实体归属、稳定性、敏感级别和有效期判断，临时情绪或未经确认的推断不应成为长期事实。记忆条目保存来源、时间、置信度和租户边界；允许更新、冲突合并、过期和用户删除。
>
> 召回时先做身份和权限过滤，再做相关性与新鲜度排序。敏感信息加密、最小化存储，禁止跨租户 embedding 检索泄漏。记忆不是越多越好，错误记忆会反复污染决策，因此要评估 memory precision 和实际任务增益。”

## 五、多 Agent、评测与生产化

### Q21：什么时候用多 Agent？常见架构有哪些？

> “单 Agent 能完成时我优先单 Agent。多 Agent 的合理动机是上下文隔离、明确专业分工、可并行的独立子任务，或者不同权限域必须隔离。它会增加通信损耗、状态一致性、循环和评测难度，不应该只是把多个角色 Prompt 放在一起。
>
> 常见架构有 supervisor-worker、路由到专家、并行 fan-out/fan-in、顺序 handoff。生产中我偏向中心化协调：由 orchestrator 保存任务图和事实状态，worker 返回结构化结果，不让它们靠无限自然语言聊天达成共识。”

### Q22：多 Agent 如何通信并处理并发冲突？

> “消息里应有 task ID、parent ID、发送方、schema 版本、幂等键和截止时间，事实状态放共享存储，消息只传引用和必要摘要。可并行的只读任务可以 fan-out，再由聚合器按规则合并；有依赖关系的任务用 DAG 或状态机调度。
>
> 多个 Agent 写同一资源时，使用数据库事务、乐观锁、租约或串行写入器，而不是让模型自行协商。冲突结果按确定性业务规则处理；无法自动裁决时保留证据并交给人。超时、重试和取消要沿任务树传播。”

### Q23：Agent 应该怎样评测？

> “Agent 是多步系统，所以我同时评最终结果和轨迹。结果层看任务成功、约束满足和产物正确性；轨迹层看工具选择、参数正确率、无效步骤、恢复能力和高风险违规；系统层看延迟、token、工具成本、人工介入率。
>
> 评测环境必须可重置，外部工具用稳定 fixture 或 sandbox，避免一次运行污染下一次。非确定性任务重复运行并报告分布，不只报最好结果。上线前离线回放，线上用小流量 A/B、守护指标和人工抽检，失败样本进入回归集。”

### Q24：Agent 可观测性要记录什么？

> “我会给一次用户任务建立根 trace，把每次模型调用、检索、工具调用和人工节点记录为 span。关键字段包括模型与 Prompt 版本、token、延迟、缓存、候选文档、工具参数摘要、结果状态、重试原因和最终验收。
>
> 日志必须脱敏，密钥和完整敏感内容不能进入 Trace。面板除了平均值，还看 P95/P99、按任务类型切片的成功率、循环深度、工具错误率和单成功任务成本。这样模型换版或 Prompt 改动后，才能知道问题出在模型、检索、工具还是编排。”

### Q25：怎样治理幻觉？

> “我先按任务拆幻觉：事实问答缺证据、结构化输出字段错误、工具参数臆造、Agent 对执行结果的错误宣称，治理方法不同。事实类用可信检索、引用和无证据拒答；结构类用 schema 和业务校验；工具类只能从真实返回值更新状态；任务完成必须通过外部验收器。
>
> Prompt 提醒和降低 temperature 只能辅助，不能作为唯一防线。真正有效的是减少模型可以自由猜测的空间、把事实锚定到数据、把关键结论外部验证，并持续维护失败样本集。”

### Q26：Prompt Injection 怎么防？

> “Prompt Injection 的本质是模型同时处理指令和不可信数据，却可能把数据中的文本误当指令。RAG 文档、网页、邮件和工具输出都可能带间接注入，单靠‘忽略恶意指令’无法彻底解决。
>
> 我的策略是纵深防御：把不可信内容标记为数据；系统策略与用户内容分层；工具最小权限和短期凭据；高风险动作人工确认；对外发、删除、付款等能力做确定性策略检查；限制网络和文件访问；输出再校验并全程审计。设计时假设模型可能被诱导，确保被诱导后仍不能越权。”

### Q27：怎样优化 Agent 的成本和延迟？

> “先按 trace 分解模型、检索、工具和排队耗时，以及每个成功任务的 token 与调用次数。常见手段是：简单意图用小模型或规则路由；稳定长前缀利用 prompt cache；工具按需加载；历史摘要和检索去重；独立工具并行；结果尽早流式返回；确定性中间步骤不用模型。
>
> 降成本不能只看单次 token，要守住任务成功率和重试率。便宜模型如果导致更多循环，单成功任务成本可能更高。我会用质量—延迟—成本三维 Pareto 比较，而不是只追求一个指标。”

### Q28：Human-in-the-Loop 应该放在哪些节点？

> “人工节点应基于风险和不确定性，而不是每一步都确认。高风险不可逆动作在执行前确认；需求歧义或关键信息缺失时先澄清；低置信度或规则冲突时升级；批量操作先展示 preview 和影响范围。
>
> 确认界面要告诉用户将执行什么、作用于谁、使用哪些数据以及能否撤销，不能只给‘允许/拒绝’。暂停时保存 checkpoint，批准后从原状态继续，并校验环境是否已变化，避免过期批准。”

## 六、Agent 答题易错清单

| 容易失分的说法                     | 更准确的回答                                                  |
| ---------------------------------- | ------------------------------------------------------------- |
| “Agent = LLM + Prompt + Tool”      | 还要有状态、循环控制、权限、验收、观测与恢复                  |
| “多 Agent 更智能”                  | 多 Agent 只在隔离、分工或并行收益覆盖协调成本时成立           |
| “MCP 替代 Function Calling”        | MCP 是连接协议，Function Calling 是模型表达工具调用的一类能力 |
| “有 Structured Outputs 就无需校验” | 仍需语义、业务、权限和截断/拒绝处理                           |
| “RAG 能消除幻觉”                   | RAG 提供外部证据，但检索和生成各自仍会失败                    |
| “向量相似度高就是答案相关”         | embedding 分数不是可跨查询解释的事实概率，还需评测和重排      |
| “上下文越长效果越好”               | 长上下文增加成本和噪声，位置利用也可能不均匀                  |
| “重试能提升稳定性”                 | 只对瞬时且安全重试的错误有效，写操作还需幂等                  |
| “模型说完成就完成”                 | 完成要由环境状态、测试或规则验收                              |
| “Prompt 能解决安全”                | 安全边界必须落在宿主权限和确定性策略上                        |
